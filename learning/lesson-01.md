# 第一课 · 把产品意图写成可验证的规格

开课先看基础短片 [软件工程在解决什么问题](../library/foundations/media/ch01.mp4) 和 [一次修改的全过程](../library/foundations/media/ch04.mp4)。读 [意图与规格](../library/foundations/ch05.md)，复制一张[空白工作纸](worksheet.md)。企业软件的角色可查 [客户那边有谁](../library/enterprise/ch01.md)，权限边界延伸读 [数据合规](../library/enterprise/ch05.md)。

## 1. 场景、规则与三类角色分工

你以 AI 产品经理身份接手客服工单台，当前处理一笔“星舟办公用品”订单：已付 200 元、已退 0 元，本次申请退款 80 元。全流程支付金额不发生变化（已付仍为 200 元、已退仍为 0 元），既有业务决策如下：

- **凭证与权限齐全**：只创建审批草案，更新工单为“等待审批”并关联该草案。
- **凭证不足**：更新工单为“等待补充材料”，必须给出原因，不建草案。
- **缺权限**：转“人工复核”，必须给出原因，不建草案。

实操前请区分三类角色，避免后续混淆职责：
- **开发 coding agent**：辅助你读代码、改页面的研发智能体，不直接替业务拍板。
- **业务 Agent**：后续结项才接入的被测执行者。入门课里由人或规则脚本办单。
- **脚本**：如页面中的`运行演示脚本`，读取当前场景的事实并调用与人相同的业务动作，没有自主判断能力，也不是改码工具。

## 2. 启动环境与手操四步

确认当前环境为 Node 20+（无需安装依赖），在你的学习副本目录执行：

```bash
node -v
npm start
```

终端会显示随机 `localhost` 端口，在浏览器打开该地址即可进入工单台。

**实操顺序（先不看答案）**：
1. 对照业务政策填写「任务卡」与「小功能需求卡」，记录你对业务边界和界面核对缺口的判断。
2. 每切换到一个新场景，先在下拉框选中它，再点初始化。换场景前导出当前运行，抄下运行编号。会用到以下操作：`初始化本场景`、`创建退款草案`、`更新工单`、`运行演示脚本`、`导出本次证据 JSON`、`归档并重新初始化`。
   - **正常分支**：点`初始化本场景` → `创建退款草案` → `更新工单`（等待审批并关联），核对已付 200 元、已退 0 元无变化。
   - **两例比较**：分别演练“凭证不足（等待补充材料）”与“缺权限（转人工复核）”，核对二者均写明原因且不建草案。
   - **错例观察**：在缺凭证案例另开新运行，故意建一份草案，再将工单置为等待补充材料、填写原因并更新。对照工单状态、草案数和动作记录，解释为什么这一单仍错，点`导出本次证据 JSON`留存记录。
   - **复位对照**：点`归档并重新初始化`恢复初始状态，再点`运行演示脚本`观察规则脚本的处理结果，与手工操作对照。

归档只封存旧运行；重新初始化会创建新编号。导出前确认当前运行号和场景相符。个人预期另存工作纸。

## 3. 引导问题

1. 正常分支结束后，为何订单已付 200 元和已退 0 元都没有变化？
2. “凭证不足”与“缺权限”分别对应不同终态，它们有哪些共同硬约束？
3. 错例中，为何容易把“表单选框出现草案”误判成“工单已关联草案”？

## 4. 教师微型示例（仅示范结构，勿照抄为个人答案）

- **任务卡格式**：`[分支]：____ ｜ [是否建草案]：____ ｜ [终态与原因]：____ ｜ [支付金额变化]：____`
- **小功能需求卡格式**：`只增加：终态区展示____；严禁改动：____。`
