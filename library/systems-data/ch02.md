## 讲义

没有索引，数据库只能从第一行开始，一行一行地看到最后一行，这叫全表扫描，表越大越慢：行数翻十倍，要看的行也翻十倍。索引是按某一列另外排好序的一份目录，记着每个值在哪几行，就像查字典，先在目录里找到在哪一页，再直接翻过去；数据库也是先在目录里找到要的值，再直接去那几行取数据，目录本身还分好几层，一千万行通常也只要三四步。索引也可以按好几列一起排，这叫组合索引，它只能从最左边的列开始用。有了索引也不一定用得上，常见的有四种情况：对列做了计算、模糊查询以通配符开头、跳过了最左边的列、一查就要返回一大半行的条件；用不用索引，由数据库自己判断。索引不是白来的：每插入一行，每一份索引都要跟着记一条，写入变慢，还多占空间；在已经很大的表上新建索引，可能跑很久、挡住正常写入，本身就是一次有风险的变更。索引用没用上别靠猜，看执行计划；给最常跑的查询里用来筛选、关联、排序的列建索引，不是越多越好。

## 术语

- **全表扫描**。 没有能用的索引时，数据库从第一行看到最后一行。表越大越慢。
- **索引**。 按某一列另外排好序的一份目录，记着每个值在哪几行。目录本身分好几层，通常三四步就能定位。
- **组合索引**。 按好几列一起排的索引，比如先按客户编号排，同一个客户里再按下单时间排。
- **最左边的列**。 组合索引排在第一位的那一列。查询里没有它，这份目录通常帮不上忙。
- **通配符开头**。 模糊查询的开头不确定，比如找名字以芳结尾的人。目录按开头排，用不上。
- **执行计划**。 数据库告诉你一条查询打算怎么找：是全表扫描，还是走了哪个索引。

## 自测

1. 订单表有一千万行，没有任何索引。要找七号客户的全部订单，数据库会怎么做？
   - A. 先查目录，再直接翻到七号客户那几行
   - B. 只查最近写入的那一部分行
   - C. 从第一行一行一行地看到最后一行
   - D. 直接跳到七号客户所在的位置

2. 索引为什么能让查找变快？
   - A. 它是按某一列排好序的目录，三四步就到
   - B. 它把整张表搬进内存，所以读起来更快
   - C. 它把查询结果提前算好，另外存了一份
   - D. 它把一张大表拆成了很多张小表来查

3. 订单表上有一个组合索引，先按客户编号排，同一个客户里再按下单时间排。下面哪条查询通常用不上它？
   - A. 查七号客户十月的订单
   - B. 只查七号客户的全部订单
   - C. 查七号客户九月到十一月的订单
   - D. 只查十月份所有客户的订单

4. 下单时间这一列有索引，但查询先把下单时间换算成日期再比较。为什么通常用不上索引？
   - A. 时间类型的列，本来就不能用来建索引
   - B. 目录里排好的是原来的值，不是算出来的
   - C. 换算太花时间，数据库等不及就放弃了
   - D. 只有带排序的查询，数据库才会用索引

5. 订单状态这一列有索引。查已支付的订单，一查就要返回一大半的行。数据库没走这个索引，最可能的原因是什么？
   - A. 已支付太常见，索引里没有收录这个值
   - B. 状态是文字，文字列上的索引不会生效
   - C. 这个索引一定是建错了，要删掉重建
   - D. 要取大半张表，数据库判断不如直接扫

6. 订单表挂着五个索引。插入一行新订单，数据库要改几处？
   - A. 一处，索引会在夜里统一补上
   - B. 六处：表一处，每个索引各一处
   - C. 五处：五个索引各一处，表不用再改
   - D. 两处：表和最常用的那个索引

<details>
<summary>展开自测答案与解释</summary>

1. **C**。 没有索引就没有目录可查。表里的行没有按客户编号排好，数据库不知道七号客户的订单在哪里，只能全部看一遍，这叫全表扫描。
2. **A**。 就像查字典：先在目录里找到在哪一页，再直接翻过去，不用从第一页翻起。目录本身还分好几层，一千万行通常也只要三四步。
3. **D**。 组合索引只能从最左边的列开始用。只知道是十月，十月的订单散在每个客户底下，这份目录通常帮不上忙。
4. **B**。 索引按列原来的值排好序。查询比较的是换算之后的结果，这份目录里没有，只能一行一行地算。
5. **D**。 一查就要返回一大半行的条件，走目录再一行行去取反而更费事，不如直接扫。用不用索引，由数据库自己判断。
6. **B**。 每插入一行，除了写表，还要把这一行记进每一份索引。所以每多一个索引，写入就多一份负担。

</details>

## 案例练习

### 一条迁移脚本和一条慢查询

订单表八千万行，晚八点是下单高峰，每秒两百单。迁移脚本 017 周五这时上线：  
CREATE INDEX ON orders(status);  
CREATE INDEX ON orders(amount);  
CREATE INDEX ON orders(note);  
CREATE INDEX ON orders(customer_id);  
CREATE INDEX ON orders(created_at);  
日报：WHERE DATE(created_at)='2026-10-07'，41 秒，没人看执行计划。

**请写出你的判断**

这条迁移脚本和这条慢查询有哪些问题？按严重程度排序，写出理由和改法。

<details>
<summary>展开案例参考分析</summary>

按对线上的影响排，至少有这四处：

- **在八千万行的大表上、晚八点高峰一次建五个索引。** 大表上新建索引要把所有行读一遍再排序，可能跑很久，期间挡住正常写入，每秒两百笔订单会卡住。这本身就是一次有风险的变更：换成不锁表的在线做法（第四章），挑低峰，一次只建一个，建完看过执行计划、确认没问题再建下一个。
- **日报查询对列做了计算，新建的索引也救不了它。** 目录里排好的是 created_at 原来的值，DATE(created_at) 是算出来的结果，通常用不上索引。把条件改成不对列做计算的写法，比如 created_at >= '2026-10-07' AND created_at < '2026-10-08'。
- **多数索引只增加写入负担。** 状态列要看查的是哪个值：查已支付这种占大头的，一查就是一大半，用不上；没有对应的常跑查询，就先别建。金额、备注也不是常跑查询里用来筛选、关联、排序的列。挂着五个索引，每插入一行要改六处，还多占空间。只给常跑查询真正需要的列建。
- **没看执行计划就加索引。** 别猜。先看这条日报查询的执行计划，确认它是全表扫描；改写条件、加一个索引之后再看一次，确认走了索引，再决定要不要留。

customer_id 上的索引本身是合理的，按客户查订单是最常跑的查询之一；created_at 上的索引在日报改写之后也用得上。这两个留下，其余三个先别建。排序依据：先排会挡住线上下单的，再排做了也解决不了问题的，最后是长期的写入负担和做事方法。

</details>

## 复习

先不看题，凭记忆写出用不上索引的四种情况，再写出多一个索引在读、写、空间上各有什么变化。

1. 全表扫描指的是什么？
   - A. 把整张表原样复制一份，留作备份
   - B. 从第一行一行一行地看到最后一行
   - C. 同时用表上的所有索引来查找
   - D. 把表里的数据按某一列重新排序

2. 组合索引只能从哪一列开始用？
   - A. 最左边的列
   - B. 最右边的列
   - C. 取值最多的列
   - D. 任意一列都行

3. 想知道一条查询是全表扫描还是走了索引，最可靠的办法是什么？
   - A. 看它跑了多久，慢就是没走索引
   - B. 数一数这张表上建了几个索引
   - C. 看这条查询的执行计划
   - D. 问写这条查询的同事

4. 应该优先给哪些列建索引？
   - A. 表里的每一列都各建一个，越全越好
   - B. 名字最长、最占空间的那几列
   - C. 最近新加进表里、还没有索引的列
   - D. 常跑查询里用来筛选、关联、排序的列

5. 在一张已经很大的表上新建索引，为什么本身就是一次有风险的变更？
   - A. 建好之后，所有查询反而一定会变慢
   - B. 要读完所有行再排序，可能很久、挡住写入
   - C. 建索引的同时会删掉表里的重复数据
   - D. 新索引一建好，原有的索引就全部失效

<details>
<summary>展开复习答案与解释</summary>

1. **B**。 没有能用的索引时，数据库只能把每一行都看一遍。行数翻十倍，要看的行也翻十倍。
2. **A**。 组合索引先按最左边的列排，再在里面按下一列排。跳过最左边的列，这份目录通常帮不上忙。
3. **C**。 执行计划直接告诉你数据库打算怎么找。别猜，加索引前后各看一次。
4. **D**。 索引不是越多越好，每多一个写入就多一份负担。只给最常跑的查询真正用得上的列建。
5. **B**。 新建索引要读完整张表再排好序。表很大时可能跑很久，期间还可能挡住正常的写入。

</details>
