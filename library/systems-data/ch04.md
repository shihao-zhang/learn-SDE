## 讲义

表的结构总要改。迁移就是把每次结构修改写成带编号的迁移脚本，放进仓库，按编号顺序执行；每个环境自己记着执行到了第几号，下次发布从下一号接着跑。代码出了问题可以退回上一版，表结构不行：删掉一列，代码退回去了，那一列的数据回不来。而且发布不是一瞬间完成的，常有一段时间新旧两版代码同时在跑，所以每一步表结构修改，都要新旧代码都能用。以把手机这一列改名叫电话为例，先扩后缩分六步：加新列，让代码两列都写（双写），回填老数据，把读切到新列，稳定运行一段时间，最后等代码不再用旧列，先备份，再删掉它。前五步出了问题都能退回去，因为旧列一直都在；只有删列退不回去，这种改动叫单向门，要单独做。光退代码救不回来的改动都算单向门，常见的有五种：删列删表、改类型、改名、回填时覆盖原值、在大表上改结构或建索引；每一种都能拆小：能退的放前面，退不回去的那一下放到最后单独做，先备份；大表换成不锁表的在线做法。备份要能恢复到出事之前，通常靠全量备份加上持续的变更日志：先恢复全量，再把日志重放到出事之前；备份要放在和数据库不同的地方，还要保留足够久。没恢复过的备份等于没有：恢复演练就是真恢复一次，恢复到新位置、不碰线上，核对条数和最近一条数据，全程计时，得出两个数：最多丢多少数据，比如能恢复到出事前五分钟，就是最多丢五分钟；恢复要多久，也就是真出事时至少要停多久。

## 术语

- **迁移脚本**。 把一次表结构修改写成带编号的脚本，放进仓库，按编号顺序执行。
- **先扩后缩**。 先加新的、两边都能用，最后才删旧的。前面每一步都能退回，只有删旧列退不回。
- **双写**。 代码写入时新旧两列都写，从这时起新写入的数据两列都有。
- **回填**。 把新列出现之前的老数据，补写进新列。
- **单向门**。 光退代码救不回来的改动，比如删列。拆小之后，把退不回去的那一下放到最后单独做，先备份。
- **恢复演练**。 真的恢复一次：恢复到新位置、不碰线上，核对条数和最近一条数据，全程计时。
- **最多丢多少数据**。 恢复出来的数据离出事那一刻差多久。比如能恢复到出事前五分钟，就是最多丢五分钟。
- **恢复要多久**。 从开始恢复到能用要花的时间，真出事时至少要停这么久。

## 自测

1. 开发环境的迁移已经执行到五号，线上还在三号。这次发布，线上会执行哪些迁移脚本？
   - A. 把一号到五号全部从头执行一遍
   - B. 只执行最近改过的那一个脚本
   - C. 由发布的人凭记忆挑出要跑的脚本
   - D. 从四号接着往下跑，执行四号和五号

2. 新代码不再用备注这一列，同事在同一次发布里顺手把它删了。发布期间会出什么问题？
   - A. 还在跑的旧代码一查备注就出错
   - B. 新代码找不到备注列，启动失败
   - C. 数据库拒绝删除还有数据的列
   - D. 没有问题，删列只影响新代码

3. 先扩后缩的六步里，为什么前五步出了问题都能退回去？
   - A. 每一步之前都先做了一次备份
   - B. 旧列一直都在，随时能切回去
   - C. 迁移脚本带编号，可以倒着执行
   - D. 新列可以随时改名，换回旧名字

4. 为什么"改名"也算单向门？
   - A. 改名会把这一列里的数据全部清空
   - B. 改了名，数据库就不允许再改回来
   - C. 只有一个名字，新旧并存时总有一边错
   - D. 改名会让这一列上的索引全部失效

5. 为什么通常在全量备份之外，还要有持续的变更日志？
   - A. 日志比全量小，可以代替全量备份
   - B. 日志能查出是谁误删的，方便追责
   - C. 有了日志，备份就不用放到别处
   - D. 先恢复全量，再重放日志到出事之前

6. 恢复演练做完，发现能恢复到出事前五分钟。这说明什么？
   - A. 真出事时，最多丢五分钟的数据
   - B. 从开始恢复到能用，要花五分钟
   - C. 出事后五分钟内必须开始恢复
   - D. 每五分钟要做一次恢复演练

<details>
<summary>展开自测答案与解释</summary>

1. **D**。 每个环境自己记着执行到了第几号，下次发布就从下一号接着跑，按编号顺序执行。
2. **A**。 发布不是一瞬间完成的，常有一段时间新旧两版代码同时在跑。旧代码还在用备注，列没了就出错。
3. **B**。 前五步都只是在旧列旁边加东西，旧列和里面的数据一直都在。只有最后删旧列这一步退不回去。
4. **C**。 一列同一时刻只有一个名字。新旧代码并存时，新代码找新名字，旧代码找旧名字，没有两边都能用的中间状态，光退代码也救不回来。
5. **D**。 只靠凌晨的一份全量，下午误删数据最多回到凌晨，白天的订单全丢。加上变更日志，可以重放到出事之前。
6. **A**。 恢复出来的数据最新只到出事前五分钟，之后的会丢，这就是最多丢多少数据。恢复要花多长时间是另一个数：恢复要多久。

</details>

## 案例练习

### 一条迁移脚本

订单表三千万行，发布时约有 15 分钟新旧代码同时在跑。迁移脚本 024 随发布执行：  
ALTER TABLE orders RENAME phone TO mobile;  
UPDATE orders SET amount = amount * 100; -- 元改成分  
ALTER TABLE orders ALTER amount TYPE bigint;  
ALTER TABLE orders DROP note;  
新代码已改成用 mobile、按分算金额、不用 note。一次做完，省得来回发布。前后都没有备份。

**请写出你的判断**

这条迁移脚本里有哪些单向门？按严重程度排序，写出每一处怎么拆：能退的放前面，退不回去的那一下放到哪里。

<details>
<summary>展开案例参考分析</summary>

四条语句各有问题，还缺了备份。按后果排：

- **原地把金额乘 100：钱会算错，而且退不回去。** 这是回填时覆盖原值。并存的 15 分钟里，旧代码还在按元写、按元读：这段时间写进来的行和被乘过一百的行混在同一列，事后分不清哪行是元、哪行是分，除以一百也改不回去。改法：加一个新列存分，双写、回填到新列、把读切过去，旧列不动。
- **前后都没有备份。** 改名、覆盖金额、删列都是光退代码救不回来的改动，挤在一次发布里，任何一步出错都没有回头路。执行前先备份，并确认能恢复到执行之前。
- **删 note：旧代码出错，数据也回不来。** 新代码不用了，但并存期间旧代码还在查 note，会出错；删掉的数据，代码退回去也回不来。改法：等所有代码都不再用 note，先备份，再单独删。
- **改名：并存期间总有一边出错。** 一列同一时刻只有一个名字，新代码找 mobile，旧代码找 phone。改法：按先扩后缩来，加新列 mobile、双写、回填、切读，稳定后再删 phone。
- **在三千万行的大表上整表改写、改类型。** 乘 100 和改类型都要动每一行，可能跑很久、挡住写入，还和发布挤在一起。改法：换成不锁表的在线做法，回填分批做，挑低峰单独执行。

拆开之后，这次发布只做加新列和双写；回填、切读放到后面几次，这些都能退回；删旧列放到最后单独做，先备份。排序依据：先排退不回去的数据和钱，再排会让线上出错或变慢的。

</details>

## 复习

先不看题，凭记忆写出先扩后缩的六步，再写出恢复演练要得出的两个数各是什么意思。

1. 先扩后缩的六步，哪个顺序对？
   - A. 加新列 → 回填 → 切读 → 双写 → 稳定 → 删旧列
   - B. 删旧列 → 加新列 → 双写 → 回填 → 切读 → 稳定
   - C. 加新列 → 双写 → 回填 → 切读 → 稳定 → 删旧列
   - D. 加新列 → 切读 → 双写 → 回填 → 删旧列 → 稳定

2. 恢复演练应该把备份恢复到哪里？
   - A. 恢复到一个新位置，不碰线上
   - B. 直接覆盖线上，才算真演练
   - C. 恢复到备份文件所在的那台机器
   - D. 不用真恢复，检查文件大小就行

3. 为什么备份要放在和数据库不同的地方？
   - A. 放在一起会拖慢数据库的读写
   - B. 放在别处，恢复起来会更快
   - C. 数据库所在的机器不允许存备份
   - D. 机器坏了，备份不能跟着一起没

4. 下面哪一种改动不是单向门？
   - A. 删掉一张不再用的表
   - B. 加一个新列，旧列不动
   - C. 回填时直接覆盖原来的值
   - D. 把金额从小数改成整数

5. 为什么备份要保留足够久？
   - A. 保留越久，恢复起来就越快
   - B. 有些错误几周后才被发现
   - C. 规定备份至少要保留一年
   - D. 保留久了就不用做恢复演练

<details>
<summary>展开复习答案与解释</summary>

1. **C**。 先加新列、开始双写，新写入的数据两列都有；再回填老数据；新列补齐了才把读切过去；稳定一段时间、代码不再用旧列后，先备份再删。
2. **A**。 演练是为了验证备份能用、量出要多久，不能拿线上数据冒险。没恢复过的备份，等于没有。
3. **D**。 备份要防的正是数据库那边出事。和数据库放在一起，机器一坏就一起没了。
4. **B**。 加新列不动任何已有的数据，退回旧代码照样能用，不用了还能删掉。先扩后缩正是从这一步开始。
5. **B**。 数据写坏了不一定马上有人发现。只保留几天的备份，救不了几周前写坏的数据。

</details>
