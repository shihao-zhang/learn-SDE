# 第 6 章　怎么读压测报告

[推理服务 · 返回课程索引](../README.md)

本章提供讲义与练习。

## 讲义

这一章教你读压测报告，挑出站不住的结论。压测是用假的流量一档一档地加压，报告一行是一档负载：每秒请求数、每秒输出 token 数、首 token 和逐 token 延迟的 p50 与 p99、错误率。p50 是中位数，p99 是一百个里九十九个不比它慢的那个值，卡顿大多藏在 p99 里；平均值最不可靠。负载低时吞吐跟着涨、延迟几乎不动，到了饱和点吞吐不再涨、延迟急剧上升；服务的能力不是吞吐的最高值，而是服务目标之内能达到的最高负载，通常在饱和点之前。过载时失败的请求不进延迟统计，延迟反而好看，所以错误率要和延迟一起看，真正算数的是有效吞吐。负载还要像真实流量：提示长度、重复提示、发送方式不对，结果都会失真。读报告按六个问题依次问：负载像不像真实、看的是不是 p99、目标之内的最高负载是多少、那一档错误率多少、瓶颈在哪、结论有没有超出测过的范围。下次遇到成本或延迟的决策，从服务目标开始算。

## 术语

- **压测**。 用假的流量一档一档地加压，看服务在每一档的表现。
- **p50**。 中位数，一半请求比它快。
- **p99**。 一百个请求里有九十九个不比它慢的那个值，用户感到的卡顿大多藏在这里。
- **饱和点**。 加压到这一档，吞吐不再上涨，延迟开始急剧上升。
- **服务能力**。 服务目标之内能达到的最高负载，通常在饱和点之前，不是吞吐的最高值。
- **错误率**。 被拒绝或超时的请求所占的比例，要和延迟一起看。
- **有效吞吐**。 每秒既满足延迟目标、又成功返回的请求数。
- **瓶颈**。 最先撑不住的那一环：首 token 先变差多半是排队或预填充；逐 token 先变差多半是批太大、长提示插进来，或显存吃紧。

## 自测

1. 报告某一档写着：首 token p50 是 0.4 秒，p99 是 1.6 秒。下面哪个理解对？
   - A. 平均要等 0.4 秒，最慢的那一个请求等了 1.6 秒
   - B. 一半请求不超过 0.4 秒，最慢的也不超过 1.6 秒
   - C. 一半不超过 0.4 秒，一百个里九十九个不超过 1.6 秒
   - D. 大多数请求的首 token 延迟在 0.4 到 1.6 秒之间

2. 每秒 2、4、8、16 个请求时，每秒输出 token 分别是 600、1,200、2,300、2,400，首 token p99 分别是 0.5、0.7、1.2、7.0 秒。饱和点大约在哪？
   - A. 在 8 和 16 之间，那里吞吐走平
   - B. 在 16 那一档，那里的吞吐最高
   - C. 在 4 和 8 之间，延迟从那里开始涨
   - D. 还没到，吞吐一直都在往上涨

3. 服务目标是首 token p99 ≤ 3 秒、错误率 < 0.1%。每秒 6、12、24 个请求时，首 token p99 分别是 1.1、2.4、8.0 秒，错误率都是 0，每秒输出 token 分别是 1,800、3,400、3,700。服务能力该写多少？
   - A. 每秒 24 个请求，那里的吞吐最高
   - B. 每秒 6 个请求，那里的延迟最低
   - C. 每秒 3,700 个 token，最高的吞吐
   - D. 每秒 12 个请求，目标之内最高的一档

4. 报告里每秒 40 个请求那一档，首 token p99 比每秒 20 个那一档还低，错误率却是 15%。最可能的解释是什么？
   - A. 负载越高，批越满，GPU 用得更充分，所以更快
   - B. 过载后部分请求被拒绝或超时，失败的不进延迟统计
   - C. 负载高时缓存命中更多，预填充省下了时间
   - D. 压测有随机误差，这一档的数字可以不管

5. 压测固定用 10 个虚拟用户轮流发请求，一个返回了再发下一个。这样测，最可能漏掉什么？
   - A. 长文档提示带来的预填充压力
   - B. 同一段提示让缓存全中的问题
   - C. 真实高峰时请求一起涌来造成的排队
   - D. 解码时每步读权重的带宽压力

6. 加压过程中，首 token p99 先急剧变差，逐 token p99 一直很稳。瓶颈多半在哪？
   - A. 批开得太大，每一步解码都变慢
   - B. 每个请求要生成的 token 太多
   - C. 解码每步读权重，显存带宽不够
   - D. 请求在排队，或者卡在预填充上

<details>
<summary>展开自测答案与解释</summary>

1. **C**。 p50 是中位数，不是平均值。p99 也不是最大值，最慢的那一个可能远超 1.6 秒。落在 0.4 到 1.6 秒之间的只有一半左右，另一半比 0.4 秒还快。
2. **A**。 从 8 到 16，负载翻倍，吞吐只多了 100，首 token p99 从 1.2 秒翘到 7.0 秒。4 到 8 时吞吐还接近翻倍，延迟只是小涨。吞吐最高的那一档，已经过了饱和点。
3. **D**。 服务能力是服务目标之内能达到的最高负载。24 那一档 p99 是 8 秒，超了目标；吞吐的最高值不是能力。12 和 24 之间没测过，也不能往上推。
4. **B**。 失败的请求没有延迟可记，留下的是成功返回的那些，延迟反而好看了。p99 漂亮、错误率百分之十五的一档，不能算达标。
5. **C**。 这样同时最多只有十个请求，前一个不回来，下一个就不发，门外永远排不起队。真实高峰时请求是一起涌来的，这部分排队测不出来。
6. **D**。 首 token 先变差，多半是排队或预填充。批太大、解码每步变慢这类问题，会先体现在逐 token 延迟上；输出多长影响的是总时间，不是首 token。

</details>

## 案例练习

### 一份压测报告

目标：首 token p99 ≤ 2 秒，逐 token p99 ≤ 100 毫秒，错误率 < 0.1%。  
每秒请求｜每秒输出 token｜首 token p50/p99 秒｜逐 token p99 毫秒｜错误率  
4｜1,000｜0.2/0.6｜33｜0  
8｜2,000｜0.3/1.2｜42｜0  
12｜2,990｜0.5/1.9｜55｜0  
16｜3,200｜2.4/8.8｜68｜20%  
20｜3,250｜1.3/4.6｜66｜35%  
所有请求用同一段 200 token 的提示。  
作者结论：①服务能力是每秒 20 个；②12 个时平均首 token 才 0.6 秒，体验很好；③饱和点在 12 到 16 之间；④上线后长文档问答也一样。

**请写出你的判断**

作者的四条结论，哪些站不住、为什么？瓶颈在哪？在这份报告的条件下，服务能力是多少？

<details>
<summary>展开案例参考分析</summary>

四条结论里只有第③条站得住。把站不住的三条和瓶颈的判断，按对上线决策的影响从大到小排：

- **服务能力不是每秒 20 个。** 那一档错误率 35%，延迟比上一档好看，是因为失败的请求不进延迟统计。服务目标之内的最高负载是每秒 12 个：首 token p99 1.9 秒，逐 token p99 55 毫秒，错误率 0。
- **长文档的结论超出了测过的范围。** 所有请求都是同一段 200 token 的提示，缓存全中，预填充几乎不花时间。长文档的预填充和显存完全是另一回事，这份报告推不出来，要用真实长度、各不相同的提示重测。
- **首 token 先变差：新请求挤不上 GPU，在门外排队。** 首 token p99 从 1.9 秒跳到 8.8 秒，逐 token p99 一直在 70 毫秒以内：已经在跑的请求还顺，新请求进不去。预填充被缓存省掉了，不是它；吞吐在每秒约 3,200 token 走平，说明能同时服务的位置满了，要加的是卡或显存。换成长文档，预填充也会压上来。
- **“平均 0.6 秒，体验很好”说明不了问题。** 目标看的是 p99。那一档 p99 是 1.9 秒，离 2 秒只差 0.1 秒，已经压线；负载又不像真实流量，上线后很可能超标。

第③条站得住：12 到 16 之间，吞吐从 2,990 只涨到 3,200，首 token p99 从 1.9 秒翘到 8.8 秒。但饱和点不是服务能力。在这份报告的条件下，能写进规划的是每秒 12 个；换成长文档问答，这个数要用真实负载重测，多半更低。

</details>

## 复习

先不看题，凭记忆写出读压测报告时依次要问的六个问题，以及判断瓶颈的两条线索。

1. 九十八个请求各用 1 秒，两个各用 50 秒。平均值和 p99 大约各是多少？
   - A. 平均约 26 秒，p99 约 50 秒
   - B. 平均约 2 秒，p99 约 50 秒
   - C. 平均约 2 秒，p99 约 1 秒
   - D. 平均约 50 秒，p99 约 2 秒

2. 一个推理服务的能力，应该看报告里的哪个数？
   - A. 服务目标之内能达到的最高负载
   - B. 压测里测到的最高每秒输出 token
   - C. 饱和点那一档的每秒请求数
   - D. 错误率开始出现之前的最高负载

3. “有效吞吐”算的是哪些请求？
   - A. 压测里发出去的所有请求
   - B. 成功返回的请求，不管等了多久
   - C. 既满足延迟目标、又成功返回的请求
   - D. 满足延迟目标的请求，包括失败的

4. 压测最高只加到每秒 16 个请求，报告却写“每秒 40 个也没问题”。这犯的是哪个错？
   - A. 只看了平均值，没看 p99
   - B. 没有把错误率和延迟一起看
   - C. 测试提示的长度不像真实流量
   - D. 结论超出了测过的范围

5. 加压过程中，逐 token p99 先变差，首 token 还好。瓶颈多半在哪？
   - A. 批开得太大，或者长提示插进来一起算
   - B. 请求在排队，或者卡在预填充
   - C. 分词太慢，切 token 跟不上
   - D. 流量太小，GPU 没有被喂满

<details>
<summary>展开复习答案与解释</summary>

1. **B**。 一共 98 + 100 = 198 秒，平均约 2 秒，看着正常；按耗时排好，第 99 个是 50 秒，p99 把慢的那一头露了出来。平均值把两个人各等的五十秒摊薄了，所以最不可靠。
2. **A**。 吞吐最高的那一档往往已经过了饱和点，延迟早就超标。能力要看服务目标之内，通常在饱和点之前；光没有错误也不够，延迟还得达标。
3. **C**。 失败的不算，慢到超出目标的也不算。只看成功率或只看延迟，都会把一部分不合格的请求算进来。
4. **D**。 16 以上一档都没测，40 时会怎样，报告里没有任何数据。读报告的最后一问，就是结论有没有超出测过的范围。
5. **A**。 逐 token 延迟先变差，多半是批太大、长提示插进来，或显存吃紧。首 token 先变差，才多半是排队或预填充；分词只占几毫秒。

</details>
