## 讲义

同一个应用发出的请求，开头往往一模一样：系统提示、工具说明、一份长文档；多轮对话每一轮还要把前面的对话重发一遍。这些相同的开头，每次都被重新预填充。前缀缓存把算过的 KV cache 留下，新请求从第一个 token 开始比对，开头完全相同的部分直接复用，只预填充后面新的那一段；它只认前缀，中间改一个字，从那里往后都要重算。命中省掉的是预填充：首 token 延迟变短，GPU 的算力省下来给别人；省不了解码，回答多长就要生成多长，所以对长输入、短输出最值钱。缓存首先放在显存里，和正在服务的请求抢同一块地方，最久没被用到的先被清掉，有的系统会挪到内存或硬盘里；有多台机器时，同一个开头的请求要送到同一台；用别人的 API，缓存也只保留一段时间，从几分钟到几天不等。主流 API 对命中缓存的输入 token 一般按正常输入价的十分之一收，九成命中时输入费降到原来的两成左右。提示要不变的在前、变的在后，别在开头写当前时间；命中率要上线后从账单或日志里实测，不要估。

## 术语

- **前缀**。 从第一个 token 开始、和之前某个请求完全相同的那一段开头；中间改了一个字，前缀就断在那里。
- **前缀缓存**。 把算过的 KV cache 留下，新请求开头完全相同的部分直接复用，只预填充后面新的部分。
- **命中**。 新请求的开头在缓存里找到了完全相同的一段，这一段不用重新预填充。
- **命中率**。 输入里命中缓存的比例，要上线后从账单或日志里实测。
- **命中的输入价**。 主流 API 对命中缓存的输入 token 一般按正常输入价的十分之一收，有的厂商第一次写入缓存还要多收两成五。
- **长输入、短输出**。 缓存最值钱的场景，比如对着同一份长文档反复提问。
- **不变的在前，变的在后**。 排提示的原则：系统提示、工具定义、参考文档放在最前，时间戳、用户名和这次的问题放在最后。

## 自测

1. 一段多轮对话进行到第 10 轮。不用任何缓存时，这一轮的预填充要算哪些内容？
   - A. 只算第 10 轮用户新说的那一句
   - B. 前 9 轮的全部对话，加上第 10 轮的新内容
   - C. 只算系统提示和第 10 轮新说的那一句
   - D. 不用预填充，接着上一轮的解码往下生成

2. 两个请求共用一段 8,000 token 的系统提示，只在第 2,000 个 token 处差了一个字，其余完全相同。第二个请求能复用多少？
   - A. 除了那一个字，其余 7,999 个 token 都能复用
   - B. 一个都复用不了，有任何差别就要全部重算
   - C. 改动处之后的部分能复用，之前的要重算
   - D. 最多复用改动处之前的 1,999 个 token，后面都要重算

3. 一个应用的缓存命中率从一成提到九成，下面哪一项基本不会变？
   - A. 首 token 延迟
   - B. 预填充占用的 GPU 算力
   - C. 回答的长度和解码要走的步数
   - D. 账单里的输入费用

4. 下面哪种场景，前缀缓存最值钱？
   - A. 对同一份 5 万 token 的合同反复提问，每次答几十字
   - B. 每次给一句很短的提示，让模型写一篇三千字的文章
   - C. 每个用户上传各自不同的长文档，每份只问一次
   - D. 同一句短提示反复使用，每次生成一份很长的报告

5. 自己部署了 4 台机器，请求随机分到任意一台。同一份长文档被反复提问，命中率却不高。最可能的原因是什么？
   - A. 机器越多，每台分到的显存越小，缓存放不下
   - B. 同一个开头被分到不同机器，每台都要各算一遍
   - C. 随机分发打乱了提示里各段内容的先后顺序
   - D. 前缀缓存只能在单独一台机器的服务上开启

6. 要让缓存多命中，提示按哪种顺序排最好？
   - A. 时间戳、系统提示、工具定义、参考文档、用户名、这次的问题
   - B. 系统提示、用户名、工具定义、参考文档、时间戳、这次的问题
   - C. 这次的问题、系统提示、工具定义、参考文档、时间戳、用户名
   - D. 系统提示、工具定义、参考文档、时间戳、用户名、这次的问题

<details>
<summary>展开自测答案与解释</summary>

1. **B**。 多轮对话每一轮都要把前面的对话重新发一遍。没有缓存，这些重复的开头每一轮都要重新预填充，轮数越多越长。
2. **D**。 前缀缓存从第一个 token 开始比对，只认完全相同的开头。在第 2,000 个 token 处对不上了，从那里往后全部重新计算，哪怕后面的内容一字不差。
3. **C**。 命中省掉的是预填充，所以首 token 延迟、算力和输入费都会降。回答有多长，还是得一步一步生成多长，解码这一段不受影响。
4. **A**。 缓存省的是相同开头的预填充。同一份长文档被反复问，能省的预填充最多；回答又短，解码那段本来就不长，省下的占比就大。长输出的场景大头在解码，缓存帮不上。
5. **B**。 缓存放在每台机器自己的显存里。同一个开头的请求散到四台，每台都得先各算一遍。把同一个开头的请求送到同一台，命中率才上得去。
6. **D**。 不变的在前、变的在后。时间戳、用户名和问题每次都可能不同，放在哪里，从那里往后就都要重算，所以都放在最后。

</details>

## 案例练习

### 账单里的命中率

一个客服应用的提示模板，从上到下：  
1. 当前时间：2026-10-08 14:23:51  
2. 系统提示前半段，1,500 token  
3. 用户：{用户名}，会员等级：{等级}  
4. 系统提示后半段，1,000 token  
5. 工具说明，8 个工具每次按随机顺序拼接，3,000 token  
6. 用户问题：{问题}  
7. 产品手册全文，2 万 token，每月更新一次  
每天约 5 万次请求，白天来得很密。上个月账单：输入 380 亿 token，其中命中缓存 8 亿；输出 4.5 亿 token。

**请写出你的判断**

找出模板里让缓存命中不了的写法，说明怎么改、为什么。再估计改完以后能省在哪一块，哪一块省不了。

<details>
<summary>展开案例参考分析</summary>

有四处写法各自把前缀截断一次，要全部改掉。从前往后看：

- **第 1 行的时间让后面全部重算。** 前缀缓存从第一个 token 开始比对，开头精确到秒，每秒都在变，后面 2.5 万 token 几乎每次都要重新预填充，这就是账单上只有约 2% 命中的原因。时间挪到最后。
- **用户名夹在系统提示中间。** 就算时间挪走了，从第 3 行起每个用户都不一样，后面的内容在不同用户之间复用不了。用户名和会员等级挪到末尾。
- **工具说明每次随机排序。** 8 个工具内容一样，顺序一变，前缀就对不上，从这里往后都要重算。改成固定顺序。
- **问题放在手册前面。** 手册 2 万 token，是每次输入里最大的一块，却跟在每次都不同的问题后面，前面三处修好了它也复用不了。手册挪到问题前面，问题放最后。
- **改完省的是输入，省不了输出。** 可复用的开头约 2.55 万 token，几乎是全部输入。命中部分一般按输入价的十分之一收，就算实际只命中九成，输入费也能降到原来的两成左右，首 token 也更快。输出那 4.5 亿 token 是解码一个一个生成的，一点也省不了。

从前往后排是有道理的：缓存只认前缀，最靠前的断点让后面全部作废，少改一处，手册那 2 万 token 都白费。“手册每月更新一次”不是问题，只是更新后的第一批请求要重算一遍；白天请求很密，同一个开头隔不了几秒就再来，也不会因为放太久被清掉。改完以后看下个月账单里命中缓存的 token 数，不要估。

</details>

## 复习

先不看题，凭记忆写出命中缓存省得了什么、省不了什么，以及提示里哪些该放前面、哪些该放后面。

1. 前缀缓存复用的是什么？
   - A. 算好的 KV cache，开头相同的部分直接拿来用
   - B. 之前生成过的回答，遇到相同问题直接返回
   - C. 模型权重，换一个请求不用重新加载一遍
   - D. 分词的结果，相同的字不用重新切一遍

2. 命中缓存，省得了哪一步，省不了哪一步？
   - A. 省得了解码，省不了预填充
   - B. 两步都能省，只是省的比例不同
   - C. 省得了预填充，省不了解码
   - D. 两步都省不了，只能省下排队

3. 缓存放在哪里？空间不够时，哪些先被清掉？
   - A. 放在显存里，最早写进去的先清掉
   - B. 放在分词器里，最久没被用到的先清掉
   - C. 放在显存里，占地方最大的先清掉
   - D. 放在显存里，最久没被用到的先清掉

4. 一份长文档反复被问，九成的输入 token 命中缓存，命中部分按正常输入价的十分之一收。输入费大约变成原来的多少？
   - A. 约一成
   - B. 约两成
   - C. 约五成
   - D. 约九成

5. 缓存命中率应该怎么得到？
   - A. 上线后从账单或日志里实测
   - B. 按提示里不变部分的占比来估算
   - C. 照厂商公布的平均命中率来算
   - D. 压测时把同一条请求重复发一千次

<details>
<summary>展开复习答案与解释</summary>

1. **A**。 它把算过的 KV cache 留下，新请求开头相同的部分不用再预填充。回答仍要重新生成，这正是它省不了解码的原因。
2. **C**。 相同的开头不用再预填充，首 token 更快，算力也省了；回答多长就要一步一步生成多长，解码一点没少。
3. **D**。 缓存和正在服务的请求抢同一块显存，不够时最久没被用到的先清掉。所以命中率还要看同一个开头隔多久再来一次。
4. **B**。 命中的九成按十分之一收，相当于原价的 0.09；没命中的一成照原价收。合起来约 0.19，也就是两成左右。算成一成是漏掉了没命中的那部分。
5. **A**。 命中率不光看提示怎么排，还看同一个开头隔多久再来、请求送到了哪台机器、缓存有没有被清掉，这些只有上线后才看得到。

</details>
