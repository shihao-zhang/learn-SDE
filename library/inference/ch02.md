## 讲义

解码每一步都要把全部权重从显存读一遍，却只生成一个 token，所以要批：同一步里放进几十个请求，权重仍只读一遍，每个请求各出一个 token，这是推理服务提高吞吐最主要的手段。静态批凑够一批一起开始、一起结束，先写完的位置只能空着，要等最长的那条，新请求在外面干等。连续批每生成一步重新排一次，写完的立刻离开，排队的马上补位，只要有人排队，GPU 上就一直是满的，vLLM、SGLang 这类主流推理框架默认这样调度。新请求补进来要先预填充，一段很长的提示会让同一批正在解码的请求顿一下；分块预填充把长提示切成几段，每一步只做一段，和别人的解码一起算，块越小别人卡得越轻，这个请求自己的首 token 越晚。批越大吞吐越高，但每一步变慢，每个用户的逐 token 延迟变长，再大显存也放不下更多的 KV cache。负载接近处理能力的上限时，排队等待会急剧上升，所以不能按刚好跑满来规划，要留余量。

## 术语

- **批处理**。 把多个请求放进同一步解码，权重只读一遍，每个请求各生成一个 token。
- **吞吐**。 整个服务每秒总共生成的 token 数。
- **静态批**。 凑够一批一起开始、一起结束，先写完的位置空着，要等最长的那条。
- **连续批**。 每生成一步重新排一次，写完的立刻离开，排队的马上补进空位。
- **分块预填充**。 把长提示切成几段，每一步只做一段，和别人的解码一起算。
- **批大小**。 同一步里一起算的请求数，越大吞吐越高，每个用户的逐 token 延迟也越长。
- **余量**。 规划时离处理能力上限留出的距离，因为接近上限时排队会急剧上升。

## 自测

1. 解码时把 30 个请求放进同一步，每一步只慢一点，产出却多了很多。关键原因是什么？
   - A. 30 个请求共用同一份 KV cache，不用各存一份
   - B. 放进同一批的请求可以跳过各自的预填充步骤
   - C. 全部权重每一步只从显存读一遍，30 个请求共用
   - D. 批处理让每个请求每一步生成好几个 token

2. 静态批里，一批 8 个请求，7 个在 50 个 token 内就写完了，1 个要写 2,000 个 token。接下来会怎样？
   - A. 7 个位置空着，等最长那条写完才整批换人
   - B. 7 个写完的立刻离开，排队的请求马上补进来
   - C. 那条长的会被中途截断，好让整批尽快换人
   - D. 7 个空位会被拿来帮那条长的一起生成，让它更快

3. 同样的流量，把调度从静态批换成连续批，最可能看到什么变化？
   - A. 每一步要读的权重变少了，解码变快
   - B. 每个请求的回答变短了，总时间缩短
   - C. 预填充可以省掉，首 token 马上出来
   - D. GPU 上空着的位置变少，排队的请求等得更短

4. 一个带 3 万 token 长文档的请求补进正在解码的批里，同批的用户反映字突然卡了一下。最对症的做法是什么？
   - A. 改回静态批，让长请求等整批结束再进来
   - B. 用分块预填充，把长提示切成几段，每一步只做一段
   - C. 把批大小调大，让长提示的预填充摊得更薄一些
   - D. 缩短其他用户的回答，让卡住的时间少一些

5. 把分块预填充的块切得更小，会怎样？
   - A. 同批其他用户卡得更轻，这个长请求自己的首 token 更晚
   - B. 同批其他用户卡得更轻，这个长请求的首 token 也更早
   - C. 这个长请求的首 token 更早，同批其他用户卡得更重
   - D. 对谁都没有影响，只是计算的先后顺序变了

6. 其他条件不变，批大小从 16 调到 64，最可能看到什么？
   - A. 每秒总 token 数下降，每个用户的逐 token 延迟变短
   - B. 每秒总 token 数上升，每个用户的逐 token 延迟变短
   - C. 每秒总 token 数和逐 token 延迟都基本不变
   - D. 每秒总 token 数上升，每个用户的逐 token 延迟变长

<details>
<summary>展开自测答案与解释</summary>

1. **C**。 解码每一步最费事的是把全部权重从显存读一遍，真正要算的很少。读一遍权重就能让 30 个请求各出一个 token，产出成倍增加。KV cache 仍是每个请求各自一份，每一步也仍然只出一个 token。
2. **A**。 静态批一起开始、一起结束。短的早就写完了，位置却只能空着等最长的那条，门外的新请求也只能干等。写完就走、马上补位是连续批的做法。
3. **D**。 连续批每生成一步就重新排一次，写完的立刻离开，排队的马上补进空位，所以 GPU 一直是满的，排队的人也不用等一整批结束。它改的是谁在什么时候上 GPU，不改每一步读多少权重，也不省预填充。
4. **B**。 卡顿来自新请求的长提示一下子占满了这一步的预填充。切成几段、每一步只做一段并和别人的解码一起算，别人就只稍微变慢。改回静态批会让空位和门外的排队又多起来。
5. **A**。 块越小，每一步夹带的预填充越少，别人的解码受影响越小；但这段长提示要分更多步才能算完，它自己的第一个字就来得更晚。块的大小是在别人和它自己之间取舍。
6. **D**。 批越大，同一步里产出的 token 越多，吞吐上升；但每一步要算的东西变多，每一步变慢，每个用户看到的字就蹦得更慢。总吞吐和单个用户的体验此消彼长。

</details>

## 案例练习

### 一份提吞吐的方案

工程师小周为了“提高吞吐、降低成本”提了一份方案。背景：在线聊天服务，用连续批，批大小上限 32，约三成请求带 2 万 token 以上的长文档。  
1. 批大小上限从 32 提到 512。  
2. 关掉分块预填充，省得调块的大小。  
3. 改用静态批，每批一起开始、一起结束，方便统计。  
4. 压测时每秒最多处理 40 个请求，就按每秒 40 个来定机器数量，不留余量。  
5. 夜里跑的离线摘要任务没人盯着看，单独部署，批大小在显存放得下的范围内开大。

**请写出你的判断**

逐条说出它对吞吐、逐 token 延迟、首 token 延迟和排队的影响，判断能不能上。不能上的按危害从大到小排序，并写出理由。

<details>
<summary>展开案例参考分析</summary>

第 5 条可以上，第 1 条要改着上，其余三条不能上。按危害从大到小排：

- **第 4 条最危险：不留余量。** 接近处理能力上限时，等待不是慢慢变长，而是急剧上升。按每秒 40 个定机器，流量稍一冒头，排队就飙升，所有人的首 token 延迟一起变长。省下的是机器钱，赔上的是每个用户的等待。
- **第 3 条和目标正好相反：静态批。** 回答长短差别很大，先写完的位置空着等最长的那条，吞吐下降；新请求要等整批结束才进得来，排队和首 token 延迟都变长。为了统计方便，丢掉的恰恰是吞吐。
- **第 2 条让别人卡顿：关掉分块预填充。** 三成请求带 2 万 token 以上的长文档，它们一补进来，整段预填充会让同批正在解码的人顿一下，逐 token 延迟忽快忽慢。只有这些长请求自己的首 token 会早一点。
- **第 1 条要改着上：批大小一档一档加。** 批变大，吞吐上升，同时上 GPU 的请求多了，排队也会短一些；代价是每一步变慢，所有人的逐 token 延迟变长。512 条里有三成是长文档，显存多半放不下这么多 KV cache。应该逐档往上调，同时盯着逐 token 延迟和显存。
- **第 5 条可以上：离线任务开大批。** 夜里的摘要没人等着看字蹦出来，逐 token 延迟变长无所谓，要的就是总吞吐。只要显存放得下，批开大正合适。

第 3、4 条谁排第一都说得通：静态批一直在伤吞吐和所有人的首 token，不留余量只在高峰出事，但一出事就是所有人一起等。理由写清楚即可；第 2 条排在它们后面没有争议。排序依据是影响面和离目标有多远：不留余量会在高峰时拖累所有人；静态批直接压低吞吐，和方案的目标相反；关掉分块只在长请求进来时伤到同一批的人；批大小是一个可以逐档试出来的数。

</details>

## 复习

先不看题，凭记忆写出静态批和连续批的区别、分块预填充的取舍，以及批大小变大时吞吐、逐 token 延迟和显存各怎么变。

1. 这一课说，推理服务提高吞吐最主要的手段是什么？
   - A. 分块预填充
   - B. 缩短回答
   - C. 缩短提示
   - D. 批处理

2. 连续批和静态批最根本的区别是什么？
   - A. 连续批的批大小比静态批大得多
   - B. 连续批每生成一步重新排一次，写完就走、马上补位
   - C. 连续批不需要做预填充，直接开始解码
   - D. 连续批会让每个请求的回答变得更短

3. 这一课说的“吞吐”指的是什么？
   - A. 单个用户每秒能看到多少个 token
   - B. 从发出请求到看见第一个字的时间
   - C. 整个服务每秒总共生成多少个 token
   - D. 同时在门外排队的请求有多少个

4. 服务平时的负载是处理能力上限的四成，几乎不用排队。负载涨到九成五时，排队时间最可能怎样？
   - A. 急剧上升，远不是按比例慢慢变长
   - B. 跟着负载按比例变长，负载多一倍等待也多一倍
   - C. 仍然几乎为零，因为还没有到达上限
   - D. 反而变短，因为 GPU 更满、效率更高

5. 批大小不能无限往上调。除了每个用户会变慢，还有什么硬限制？
   - A. 批越大，模型回答的精度越低
   - B. 分词器一次只能处理固定数量的请求
   - C. 显存放不下更多请求的 KV cache
   - D. 连续批只支持一个固定的批大小

<details>
<summary>展开复习答案与解释</summary>

1. **D**。 解码每一步读一遍权重只出一个 token；把很多请求放进同一步，权重只读一遍就能出很多个 token。分块预填充解决的是卡顿，不是吞吐。
2. **B**。 静态批凑够一批一起开始、一起结束，要等最长的那条；连续批每一步都重新安排谁在 GPU 上，只要有人排队，就不会有空着的位置。
3. **C**。 吞吐是整个服务的总量。单个用户看到字蹦得多快由逐 token 延迟决定；批越大，前者越高，后者反而越慢，两者不能混为一谈。
4. **A**。 离上限还远时几乎不用排；一接近上限，等待不是慢慢变长，而是急剧上升。所以不能按刚好跑满来规划，要留余量。
5. **C**。 每个请求的 KV cache 都占着显存，直到请求结束。批越大，同时占着的 KV cache 越多，再大就放不下了。

</details>
