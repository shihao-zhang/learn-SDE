# 第 5 章　延迟、吞吐、成本与容量规划

[推理服务 · 返回课程索引](../README.md)

本章提供讲义与练习。

## 讲义

这一章把前面的旋钮放到一起算账。批开大、多加卡、量化，都在延迟、吞吐、成本之间交换，没有哪个设置三样都最好，所以先定服务目标，再在目标之内把成本压到最低。服务目标要写成能检查的分位数，比如首 token 延迟 p99 不超过 2 秒、逐 token 延迟 p99 不超过 100 毫秒、错误率低于千分之一；聊天最看首 token，批量处理几乎只看吞吐和成本。用 API 时，一次请求的成本是输入 token 乘输入价加输出 token 乘输出价，输出价通常是输入价的三到八倍，推理模型回答前的思考也按输出收费。自己部署时，容量从显存算起：一张八十 GB 的卡留一成余量，放下权重，剩下的给 KV cache；每个 token 的 KV cache 键和值各一份，等于 2 乘层数、KV 头数、每头维度和每个数的字节数。由此算出的是并发数，不是每秒请求数，两者的关系是：并发数等于每秒到达的请求数乘每个请求平均停留的秒数；这只是显存给的上限，算力可能先到顶，要靠压测确认。成本反过来算：卡每小时的价格除以满足服务目标时每小时生成的 token 数。这是满负荷的数，真实流量平均只用到一半，成本就翻倍，自建便宜的前提是把卡喂满。

## 术语

- **服务目标**。 用能检查的数写下的要求，比如首 token 延迟 p99 不超过 2 秒、错误率低于千分之一。
- **p99**。 九十九分位：一百个请求里有九十九个不比它慢。
- **并发数**。 同时在服务的请求数，不是每秒来多少个请求。
- **输出 token**。 按输出价计费的 token。推理模型回答前的思考也算输出，估算时用账单里的实际输出数。
- **显存余量**。 显存不能用满，先留出一成，剩下的再分给权重和 KV cache。
- **每 token 的 KV cache**。 2 × 层数 × KV 头数 × 每头维度 × 字节数，开头的 2 是键和值各一份。
- **每百万 token 成本**。 卡每小时的价格，除以每小时生成的 token 数（以百万计）。
- **满负荷**。 卡一直被喂满的状态。按它算出的成本最低；真实流量平均只用到一半，成本就翻倍。

## 自测

1. 把批开大，延迟、吞吐、成本会怎么变？
   - A. 吞吐上去，延迟也变短，代价是多花一些钱
   - B. 延迟、吞吐、成本三样都变好，代价是赌精度
   - C. 吞吐上去，每个 token 更便宜，单个用户等得更久
   - D. 吞吐不变，每个 token 更便宜，单个用户等得更久

2. 一个夜里批量给文档打标签的任务，没有人在线等结果。它的服务目标最该盯什么？
   - A. 吞吐和每个 token 的成本
   - B. 首 token 延迟的 p99
   - C. 逐 token 延迟的 p99
   - D. 首 token 延迟的 p50

3. 一次请求输入 4,000 token、输出 1,000 token，价格是每百万输入 token 3 美元、每百万输出 token 15 美元。一次请求约多少钱？
   - A. 约 0.015 美元
   - B. 约 0.063 美元
   - C. 约 27 美元
   - D. 约 0.027 美元

4. 一个模型有 40 层、8 个 KV 头、每头维度 128，KV cache 用十六位存（每个数 2 字节）。每个 token 的 KV cache 约多少？
   - A. 约 80 KB
   - B. 约 160 KB
   - C. 约 20 KB
   - D. 约 160 MB

5. 显存算下来，一张卡最多同时跑 120 个请求，每个请求平均停留 8 秒。下面哪个说法对？
   - A. 每秒最多 15 个，这只是显存的上限，要压测确认
   - B. 每秒能接 120 个，这就是这张卡的服务能力
   - C. 每秒能接 960 个，因为每个请求要停留 8 秒
   - D. 每秒能接 15 个，直接按这个数做规划就行

6. 一张卡每小时 2.7 美元，压测测出满足服务目标时每秒生成 1,500 个 token。真实流量平均只用到一半。每百万输出 token 实际约多少钱？
   - A. 约 0.5 美元
   - B. 约 0.25 美元
   - C. 约 1 美元
   - D. 约 1,000 美元

<details>
<summary>展开自测答案与解释</summary>

1. **C**。 批开大，是用单个用户的等待换总吞吐，吞吐高了，每个 token 就便宜。延迟吞吐都变好但多花钱的是加卡，又快又省但赌精度的是量化。
2. **A**。 没人在线等，首 token 和逐 token 快不快都不要紧。聊天才最看首 token，批量处理几乎只看吞吐和成本。
3. **D**。 4,000 × 3 ÷ 1,000,000 = 0.012，1,000 × 15 ÷ 1,000,000 = 0.015，合计 0.027 美元。0.015 是全按输入价算，或者只算了输出；0.063 是把两个价格弄反了；27 美元是把每百万当成了每千。
4. **B**。 2 × 40 × 8 × 128 × 2 = 163,840 字节，约 160 KB。开头的 2 是键和值各一份，漏了就是 80 KB；漏乘 KV 头数是 20 KB；160 MB 是单位差了一千倍。
5. **A**。 并发数 = 每秒到达数 × 平均停留秒数，所以每秒最多 120 ÷ 8 = 15 个。120 是同时在跑的个数，不是每秒请求数。15 也只是显存给的上限，算力可能先到顶。
6. **C**。 1,500 × 3,600 = 540 万 token 每小时，2.7 ÷ 5.4 = 0.5 美元，这是满负荷的数。平均只用一半，每小时照付 2.7 美元却只生成 270 万个 token，成本翻倍到约 1 美元。0.25 是把方向弄反了。

</details>

## 案例练习

### 一页容量规划

80 GB 的卡；高峰每秒 20 个请求，平均是高峰一半；每个请求 4,000 token、停留 10 秒。  
1. 目标：平均首 token 延迟 ≤ 1 秒。  
2. 权重：80 亿参数×2 字节 = 16 GB。  
3. 每 token KV cache = 32 层×8 头×128 维×2 字节 = 64 KB。  
4. 80 − 16 = 64 GB，放 100 万 token，即每秒 250 个请求，一张卡够。  
5. 卡每小时 3 美元，压测每秒 2,000 token，每百万 0.4 美元，比 API 便宜。

**请写出你的判断**

这是同事写的一页容量规划。找出里面的错误，按后果从重到轻排序，并写出正确的算法和结果。

<details>
<summary>展开案例参考分析</summary>

第 2 条算对了，第 5 条的算术也对，但前提错了。其余的错会一路传下去。按后果从重到轻：

- **把并发数当成了每秒请求数。** 100 万 ÷ 4,000 = 250，是同时在跑的个数，不是每秒请求数。每秒能接的 = 并发数 ÷ 平均停留秒数：就算按他的 250，也只有每秒 25 个；按正确的约 110，只有每秒 11 个。高峰每秒 20 个，要同时服务 20 × 10 = 200 个，两张卡约 220 个位置已经九成多满，留出余量要三张，算力够不够还要压测确认。
- **能放下的 token 数算多了一倍多。** 公式漏了开头的 2（键和值各一份），每 token 应是 2 × 32 × 8 × 128 × 2 字节 = 128 KB；也没留一成余量，应是 80 × 0.9 − 16 = 56 GB。56 GB 只放得下四十多万个 token，约 110 个请求，不是 250。
- **成本按满负荷算了。** 2,000 × 3,600 = 720 万 token，3 ÷ 7.2 ≈ 0.4 美元，算术没错，但这是卡一直被喂满的数。按高峰配卡，全天平均只用到一半，实际约 0.8 美元。和 API 比时不能拿它对 API 的输出价：这个数已经包含处理输入的成本，API 的输入另收钱。要按同样的请求量，各算一个月的总账再比。
- **服务目标用了平均值。** 要写成能检查的分位数，比如首 token 延迟 p99 ≤ 2 秒。p99 管住的是一百个里的九十九个，平均值管不住慢的那一头。

排序看的是上线后谁先出事：并发数和 KV cache 两处错叠在一起，会让高峰流量直接压垮一张卡；成本那处让自建看起来便宜一半，影响买不买卡的决定；服务目标不改，压测时就量错了东西。

</details>

## 复习

先不看题，凭记忆写出从一张卡的显存一步步算到每秒能接多少请求的过程，以及每百万 token 成本的算法。

1. 服务目标写着“首 token 延迟 p99 ≤ 2 秒”。它的意思是什么？
   - A. 所有请求的首 token 延迟平均不超过 2 秒
   - B. 每一个请求的首 token 延迟都不超过 2 秒
   - C. 一半请求的首 token 延迟不超过 2 秒
   - D. 一百个里有九十九个的首 token 延迟不超过 2 秒

2. 主流 API 的输出价，通常是输入价的几倍？
   - A. 差不多一样
   - B. 三到八倍
   - C. 十到二十倍
   - D. 大约一半

3. 并发数和每秒请求数之间是什么关系？
   - A. 并发数 = 每秒到达的请求数 × 每个请求平均停留的秒数
   - B. 并发数 = 每秒到达的请求数 ÷ 每个请求平均停留的秒数
   - C. 并发数就等于每秒到达的请求数，两个是同一个数
   - D. 并发数 = 每秒请求数 × 每个请求的平均 token 数

4. 每个 token 的 KV cache = 2 × 层数 × KV 头数 × 每头维度 × 字节数。开头的 2 代表什么？
   - A. 十六位每个数占两个字节
   - B. 预填充和解码各存一份
   - C. 键和值各要存上一份
   - D. 给显存留出一倍余量

5. 延迟、吞吐、成本没法三样都最好。做规划时的顺序是什么？
   - A. 先把成本压到最低，再看延迟能做到多少
   - B. 先把吞吐做到最高，再按吞吐来定价格
   - C. 三样各让一步，取一个折中的设置
   - D. 先定服务目标，再在目标之内把成本压到最低

<details>
<summary>展开复习答案与解释</summary>

1. **D**。 p99 是九十九分位：一百个请求里有九十九个不比它慢。一半请求不超过的那个数是 p50；要求每一个都不超过，又是另一回事。
2. **B**。 所以输出长的请求更贵。算一次请求的成本，输入和输出要分开，各乘各的价格。
3. **A**。 同时在服务的个数，取决于来得多快、每个待多久。显存给出的是并发上限，除以平均停留秒数，才是每秒能接的请求数。
4. **C**。 KV cache 存的是每个 token 的键和值，所以乘 2。字节数是公式里单独的一项，余量是在显存总数上先留一成。
5. **D**。 服务目标定下什么算够用，在够用的前提下，剩下的就是省钱。先压成本，常常会压到用户等不了。

</details>
