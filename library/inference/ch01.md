## 讲义

训练是跑一次、看最终指标；服务要应付源源不断的请求，每一个都要尽快拿到回答，每一个都在花钱。本章跟着一个请求走六站：请求、排队、预填充、KV cache、解码、返回。请求先被分词，token 是这一行的计量单位，延迟和钱都按它算；GPU 上的位置都占满时请求要排队，排队时用户一样在等。预填充把整段提示一次送进模型，为每个位置算出键和值存进 KV cache，主要吃算力，提示越长越久，结束时给出第一个 token。解码每一步只生成一个 token，每一步都要把全部权重和这条请求的 KV cache 从显存读一遍，主要受显存带宽限制；KV cache 随生成变长，一直占着显存到请求结束。流式返回带来两个延迟：首 token 延迟包括排队和预填充，逐 token 延迟决定字往外蹦得多快；总时间约等于首 token 延迟加逐 token 延迟乘输出 token 数。这条路上有四个旋钮：GPU 显存、批调度器、缓存、量化模型。

## 术语

- **token**。 分词器把文字切成的、模型认识的单位，延迟和钱都按它算；同一段话换一个模型，切出的个数就不同。
- **排队**。 GPU 上的位置都占满时，请求在门口等着轮到它，这段时间用户一样在等。
- **预填充**。 把整段提示一次送进模型，并行算出每个位置的键和值存进 KV cache，主要吃算力，结束时给出第一个 token。
- **KV cache**。 算出来的键和值，存在显存里供解码每一步读取，随生成越来越长，一直占到请求结束。
- **解码**。 每一步只生成一个 token 再接回去，每一步都要把全部权重和 KV cache 从显存读一遍，主要受显存带宽限制。
- **流式返回**。 生成一个 token 就往外送一个，用户看到字一个一个蹦出来。
- **首 token 延迟**。 从发出请求到看见第一个字的时间，包括排队和预填充。
- **逐 token 延迟**。 第一个字之后，相邻两个 token 之间隔多久，决定字往外蹦得多快。

## 自测

1. 同一段 1,000 字的中文提示，换到另一家模型的 API 上，计费的输入 token 数变了。最可能的原因是什么？
   - A. 两个模型的分词器不同，同一段话切出的 token 数不一样
   - B. 另一家把排队等待的时间也折算成 token 计费了
   - C. 另一家的预填充更慢，所以计出来的 token 更多
   - D. 另一家的 KV cache 更大，每个字要多占几个 token

2. 服务端记录：一个请求从收到到给出第一个 token 用了 3 秒，其中从开始预填充到给出第一个 token 只用了 0.4 秒。剩下的 2.6 秒最可能花在哪？
   - A. 解码前几个 token，要一个一个地生成
   - B. 把算好的键和值写进 KV cache
   - C. 排队：GPU 上的位置占满了，请求在等着轮到它
   - D. 流式返回：字要一个一个地传给用户

3. 预填充主要吃算力，而不像解码那样受显存带宽限制。原因是什么？
   - A. 预填充时不用从显存读取模型权重，只管计算
   - B. 整段提示的 token 可以并行计算，一次要算的东西很多
   - C. 预填充只为第一个 token 算键和值，其余位置跳过
   - D. 预填充时 KV cache 还是空的，不占用任何显存

4. 解码阶段 GPU 的算力只用了一小截，生成却还是一步一步地慢。原因是什么？
   - A. 每一步都要把整段提示从头重新预填充一遍
   - B. 要等门外排队的请求全部轮完，才能继续解码
   - C. 每一步要并行生成很多个 token，彼此互相等待
   - D. 每一步都要把全部权重和 KV cache 从显存读一遍

5. 一个请求要输出 2,000 个 token。它的 KV cache 在显存里的占用怎么变化？
   - A. 预填充结束时就整块释放，解码阶段不再占显存
   - B. 大小在预填充时就定了，解码过程中不再变化
   - C. 随生成越来越大，一直占到请求结束才释放
   - D. 每生成一个 token 就清掉旧的，始终只占一小块

6. 一个请求的首 token 延迟是 3 秒，之后逐 token 延迟 40 毫秒，输出 500 个 token。总时间大约多少？
   - A. 约 23 秒
   - B. 约 20 秒
   - C. 约 3 秒
   - D. 约 203 秒

<details>
<summary>展开自测答案与解释</summary>

1. **A**。 token 是分词器切出来的，不同模型的分词器切法不同，同一段话的个数就不同。排队和预填充的快慢影响的是时间，不改变 token 的个数。
2. **C**。 第一个 token 在预填充结束时给出，解码和流式返回都在它之后；写 KV cache 是预填充的一部分，已经算在 0.4 秒里。预填充开始之前，GPU 上的位置占满时请求只能排队，首 token 延迟把这段也算在内。
3. **B**。 预填充把整段提示一次送进模型，每个位置都要算出键和值，而且可以同时算，算力一下子就打满了。解码正相反：每一步只出一个 token，读一遍权重却算得很少。
4. **D**。 解码每一步只生成一个 token，真正要算的很少，但全部权重和这条请求的 KV cache 每一步都得从显存读一遍，所以卡在显存带宽上。提示的键和值已经存在 KV cache 里，不用每一步重新预填充。
5. **C**。 每生成一个 token，KV cache 就长一截；解码每一步都要读它，所以不能中途清掉。输出越长，这条请求占的显存越多，占得也越久。
6. **A**。 总时间约等于首 token 延迟加逐 token 延迟乘输出 token 数：3 + 0.04 × 500 = 23 秒。20 秒漏掉了第一个字之前的等待，203 秒是把 40 毫秒当成了 0.4 秒。

</details>

## 案例练习

### 回答太慢，先拧哪里

用户反馈：“点了发送，好几秒没动静，还以为卡死了。出字以后倒还顺，就是一个回答要半分钟才写完。”  
一次典型请求的实测：分词 2 毫秒，排队 2.4 秒，预填充 0.3 秒，逐 token 延迟 35 毫秒，输出 900 个 token。  
同事提的改法：  
A. 把系统提示缩短一半。  
B. 换一个更快的分词器。  
C. 高峰时段多开几台 GPU，减少排队。  
D. 回答默认先给要点，控制在 300 个 token 以内。  
E. 关掉流式返回，整段生成完再一次性显示，看起来更整齐。

**请写出你的判断**

用户等待的大头在哪？A 到 E 哪几条有用，哪条有害？把有用的按优先级排序，并写出理由。

<details>
<summary>展开案例参考分析</summary>

先把等待拆成两段，再看每条改法拧的是哪一段。按优先级排：

- **先拆账。** 首 token 延迟约 2.4 + 0.3 = 2.7 秒，其中排队占了近九成；总时间约 2.7 + 0.035 × 900 ≈ 34 秒，其中解码约 31.5 秒。用户的两句抱怨正好对应这两段。
- **C 排第一：减少排队。** “好几秒没动静”几乎全是排队造成的。排队消掉以后，首 token 延迟能从 2.7 秒降到 0.3 秒左右。代价是多开机器要多花钱。
- **D 排第二：缩短输出。** 解码占了总时间的大头。输出从 900 降到 300 个 token，总时间从约 34 秒降到约 13 秒。它不直接改变单个请求的首 token 延迟，但每个请求占着 GPU 的时间短了三分之二，排队也会跟着缓解。
- **A、B 拧的不是瓶颈。** 预填充一共才 0.3 秒，提示减半最多省下其中一部分；分词只有 2 毫秒。这两条做了，用户几乎感觉不到。
- **E 不能做。** 关掉流式，用户要等整段生成完才看见第一个字，大约 34 秒，正好把第一句抱怨放大了十几倍。

排序依据是用户最先抱怨的那一段：“没动静”说的是首 token 延迟，所以 C 在前；如果用户主要嫌写完太慢，D 就该排第一，两条其实都要做。A 本身不是错的改法，提示很长、预填充占大头时它就排得上号。另外，D 还会间接减少排队，把 D 排第一也说得通，写清理由即可。

</details>

## 复习

先不看题，凭记忆按顺序写出六站和四个旋钮，再写出一次请求总时间的估算式。

1. 一个请求依次经过的六站，正确的顺序是哪一个？
   - A. 请求、预填充、排队、KV cache、解码、返回
   - B. 请求、排队、预填充、KV cache、解码、返回
   - C. 请求、排队、解码、KV cache、预填充、返回
   - D. 请求、排队、KV cache、预填充、解码、返回

2. 首 token 延迟包括哪几段？
   - A. 只有预填充
   - B. 预填充和全部解码
   - C. 排队和全部解码
   - D. 排队和预填充

3. 用户说：“第一个字出来得挺快，后面却像挤牙膏，一个字一个字往外蹦。”该先看哪个指标？
   - A. 逐 token 延迟
   - B. 首 token 延迟
   - C. 排队时间
   - D. 预填充时间

4. 关于四个旋钮，下面哪一句说对了？
   - A. 缓存决定同时能服务多少人
   - B. 量化模型让相同的开头不必重复预填充
   - C. 批调度器决定哪些请求一起上 GPU
   - D. GPU 显存决定一个回答输出多少个 token

5. 预填充和解码，各自主要受什么限制？
   - A. 预填充受显存带宽限制，解码主要吃算力
   - B. 预填充主要吃算力，解码受显存带宽限制
   - C. 两者都主要吃算力，只是预填充算得更多
   - D. 两者都主要受显存带宽限制，解码更明显

<details>
<summary>展开复习答案与解释</summary>

1. **B**。 先排队等 GPU，轮到了才预填充；预填充算出的键和值写进 KV cache，解码每一步都要读它；生成的 token 流式返回。
2. **D**。 首 token 延迟从发出请求算到看见第一个字。第一个 token 在预填充结束时给出，所以排队和预填充都在里面，解码在它之后。
3. **A**。 第一个字之后蹦得多快，由相邻两个 token 之间隔多久决定。排队和预填充都算在首 token 延迟里，而用户说那一段不慢。
4. **C**。 GPU 显存装着权重和所有请求的 KV cache，决定同时能服务多少人；缓存让相同的开头不必重复预填充；量化模型把权重变小，让解码更快。
5. **B**。 预填充把整段提示并行算完，要算的多；解码每一步只出一个 token，却要把全部权重和 KV cache 读一遍，读得多、算得少。

</details>
