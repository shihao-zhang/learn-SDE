用于入门第二课。重点看怎样把交付范围写进计划，并检查实际改动是否落在那个范围内。

## 讲义

代码由 agent 写，你对结果负责，意思是三件事：动手之前看过计划，过程中每一步都有记录，合入之前读得懂改了什么。先让 agent 只出计划，重点看有没有难回头的步骤，以及有没有比预想大得多的地方。版本协作有三条纪律：主干保持可用，一次提交只做一件事并写清为什么改，修改通过合并请求进主干。让 agent 小步走，每完成一步就提交一次、检查一次。读改动对比按四步：改了哪些文件，删了什么，测试是加了还是少了，有没有碰到密码、权限和数据。

## 术语

- **计划**。 动手写代码之前的一份说明：改哪些文件，数据存成什么结构，分几步做，每步怎么验证。
- **难回头的步骤**。 做了之后再想改代价很大的步骤，比如定下数据的结构。
- **分支**。 从主干分出去的一条线，修改先在上面做，不影响主干。
- **提交**。 把一小组修改连同一段说明存进仓库的一次记录。
- **提交说明**。 附在每次提交上的文字，要写清为什么改。
- **改动对比**。 一次修改前后的差别清单，列出哪些行被删了，哪些行是新加的。
- **小步走**。 每完成计划里的一步就提交一次、检查一次，出了问题只需退回一小步。
- **约定文件**。 项目里一个很短的文件，写着 agent 从代码里看不出来、每次开工都要先读的规矩。

## 自测

1. agent 的计划有四步：新建抓取脚本；把记录存成每行一条、逗号分隔的文件；给页面加标题；写使用说明。哪一步最需要你在批准前想清楚？
   - A. 新建抓取脚本，因为它的代码量最大
   - B. 给页面加标题，因为用户第一眼看到
   - C. 记录存成什么结构，因为定了就难回头
   - D. 写使用说明，因为它决定别人会不会用

2. 你预想这个功能改两三个文件就够了。agent 给出的计划却要新建和修改十四个文件。你最合理的反应是什么？
   - A. 先停下，它很可能理解错了要做的事
   - B. 批准，文件多说明它考虑得比较周全
   - C. 批准，等它写完再从改动里看问题
   - D. 要求它把十四个文件拆成十四次提交

3. agent 把计划里的五步一口气做完，约九百行，只提交了一次。检查发现结果不对。这种做法最大的问题是什么？
   - A. 九百行的代码太多，运行起来会变慢
   - B. 提交次数太少，仓库的历史不够好看
   - C. 五步放在一起，提交说明会写得太长
   - D. 不知道是哪一步引入的，无从下手

4. 项目只有你一个人。agent 建议：“没有别人要看，直接提交到主干更省事，合并请求可以省掉。”你怎么判断？
   - A. 接受，合并请求是给多人协作准备的
   - B. 不接受，合并请求是留给自己停下来看的
   - C. 接受，但要求它把提交说明写得更详细
   - D. 不接受，因为直接提交到主干会丢失历史

5. agent 汇报：“全部测试通过。”你看改动对比，发现测试文件删了三个测试，没有新增。你该怎么理解这句汇报？
   - A. 要先问清为什么删，通过可能是删出来的
   - B. 通过就是通过，测试的数量不影响结论
   - C. 测试少了跑得更快，这算是一项优化
   - D. 删掉的应该是重复的测试，不必再追问

6. 你发现这是第三次对 agent 说“不要自动删除旧的数据文件”。最合适的做法是什么？
   - A. 每次开工时再提醒它一遍，保险起见
   - B. 把这句话写进项目的约定文件
   - C. 把完整的对话记录存进仓库让它读
   - D. 把这句话写进规格的非目标一栏里

<details>
<summary>展开自测答案与解释</summary>

1. **C**。 数据的结构一旦定下，后面的代码和已经存下的数据都依赖它，改起来代价最大。代码量大不等于难回头，脚本写错了可以重写。
2. **A**。 比预想大得多，通常意味着它理解错了。等写完再看最有迷惑性：那时你面对的是十四个文件的改动，比现在问一句贵得多。
3. **D**。 小步走的好处在于：出了问题，你知道是刚才那一小步引入的，退回去也只损失一小步。一次做完就失去了这个定位的能力。
4. **B**。 哪怕只有一个人，修改也在分支上做，经合并请求进主干，给自己留一个停下来看的机会。直接提交到主干不会丢历史，问题在于少了这一关。
5. **A**。 读改动的第三步就是看测试是加了还是少了。会失败的测试被删掉之后，剩下的当然全部通过，这句汇报就不能说明什么了。
6. **B**。 反复说的话就该进约定文件，agent 每次开工都会读。这个文件要短，所以存整段对话不行。非目标说的是这个工具不做什么功能，管不了 agent 干活的方式。

</details>

## 案例练习

### 回复一个合并请求

计划第 3 步：加按日期筛选，改 filter.py 和 app.py，新增 test_filter.py。agent 的合并请求如下。  
标题：完成第 3 步  
说明：实现了日期筛选，顺手整理了存储部分，测试全部通过。  
改动：filter.py 增 85 删 4；app.py 增 22 删 6；storage.py 增 40 删 130；config.py 增 3，含一行明文访问密钥；test_filter.py 增 30；test_storage.py 删 45。

**请写出你的判断**

你会合入、打回，还是要求修改？写出你的回复要点和理由，并按严重程度从高到低排序。

<details>
<summary>展开案例参考分析</summary>

打回，不合入。读改动的四步里每一步都有问题，要求它把日期筛选单独拆出来重新提交。按严重程度排：

- **计划外大量删除存储代码。** storage.py 不在第 3 步的计划里，却删了 130 行。删除比新增更危险，而且它碰的是数据怎么存。
- **存储的测试被删了 45 行。** 能发现存储被改坏的测试，和存储的改动一起消失了。说明里的“测试全部通过”因此不能作数。
- **访问密钥明文写进了代码。** 密钥属于机密，要单独保管，不写在代码里。合入主干就等于把它留在了仓库里。
- **一个请求做了两件事。** 日期筛选和整理存储应该分开。分开之后，筛选那一份只有三个文件，几分钟就能读完。
- **说明没有讲为什么。** “顺手整理”没有解释存储部分为什么要动。说明要写清为什么改，光说改了什么不够。

这道题练的是只看文件列表和增删行数就做出决定，一行代码都不用读。排序看的是后果能不能挽回：数据和它的测试排最前，密钥其次，拆分和说明是流程上的问题。

</details>

## 复习

先不看题，凭记忆写出负责的三件事、版本协作的三条纪律，以及读改动的四步。

1. 读改动对比，第一步先看什么？
   - A. 每一行新代码的语法细节
   - B. 新增的行数是不是太多
   - C. 改了哪些文件，有无计划外的
   - D. 提交说明里有没有错别字

2. 读改动时，删除的行和新增的行，哪一种更要留心？
   - A. 删除的行，被删掉的可能是原本在起作用的东西
   - B. 新增的行，因为新代码还没有经过任何检查
   - C. 两种一样，都按行数的多少来分配注意力
   - D. 都不用留心，持续集成会替你全部把关

3. 一条好的提交说明，最该写清什么？
   - A. 改动了哪几行代码
   - B. 这次提交花了多长时间
   - C. 是哪个 agent 写的代码
   - D. 为什么要做这次修改

4. 审 agent 的计划时，重点看哪两样？
   - A. 文件的命名和代码的风格
   - B. 难回头的步骤和特别大的地方
   - C. 步骤的数量和预计的时间
   - D. 用了哪些依赖和哪个版本

5. 三条纪律里，对主干的要求是什么？
   - A. 主干只允许你本人直接修改
   - B. 主干每周合入一次修改就够了
   - C. 主干永远保持可用，修改在分支上做
   - D. 主干上的每次提交都要超过一百行

<details>
<summary>展开复习答案与解释</summary>

1. **C**。 四步的顺序是：改了哪些文件，删了什么，测试增减，有没有碰密码、权限和数据。不需要逐行读懂语法。
2. **A**。 删除比新增更危险。所以读改动的第二步专门看删掉了什么。
3. **D**。 改了什么从改动对比里就能看到。为什么改只有写下来才留得住。
4. **B**。 难回头的步骤要在动手前想清楚，比如数据的结构。比预想大得多的地方，通常意味着它理解错了。
5. **C**。 修改都在分支上做，经合并请求才进主干。这样主干上的版本随时是能用的。

</details>
