用于入门第一课。沿着意图、规格、实施、验证与发布的顺序，找出每一步应由谁判断，以及下游需要什么证据。

## 讲义

一次修改从头到尾要过六个关口：意图、规格、计划、评审、发布、分诊，每个关口只擅长拦一类错。意图和规格检验做的是不是该做的事；计划看影响半径；评审和持续集成都通过才能并入主干，agent 的自检不算关口。并入主干不等于上线，发布由人放行，之后分批放量，每一级停下来看指标。上线后出了异常先恢复再查因，删数据这类单向门要单独发布，每次事故都变成一条回归测试。agent 负责起草和执行，人负责签字。

## 术语

- **关口**。 流程里要有人签字才能往下走的检查点，每个关口只擅长拦一类错。
- **意图**。 要解决什么问题，值不值得做。
- **规格**。 把“做成什么样算完成”写下来的文档。
- **影响半径**。 一次修改会波及多远。
- **自检**。 写代码的一方自己跑测试、自己检查，不算关口。
- **分批放量**。 新版本先给百分之一的用户，再逐级扩大，每一级停下来看指标。
- **分诊**。 上线后发现异常时，由人决定立刻回退、排期修，还是忽略。
- **单向门**。 做了就退不回去的修改，比如删数据。

## 自测

1. agent 写完代码后报告：“测试全部通过，已完成自检。”同事说，既然这样评审可以省了。问题在哪？
   - A. agent 跑的测试数量可能不够
   - B. 自检结果没有贴到合并请求上
   - C. 应该让 agent 再自检一遍确认
   - D. 写的一方不能给自己打分

2. 一个合并请求改了 60 个文件、4000 行，评审人半小时后批准了。最该担心什么？
   - A. 评审人可能不是这块代码的负责人
   - B. 修改太大没人读得完，评审形同虚设
   - C. 持续集成跑这么多代码可能会超时
   - D. 评审时间太短，应规定至少两小时

3. 一次修改昨天并入了主干。今天有同事对客户说：“这个功能已经上线了。”这句话错在哪？
   - A. 并入主干后还要发布放行和分批放量
   - B. 并入主干后还要再做一次代码评审
   - C. 并入主干后还要等持续集成跑完
   - D. 并入主干后还要产品负责人来验收

4. 新版本放量到 10% 时，出错比例明显上升。值班的人说：“先别动，我查清原因再决定。”更好的做法是什么？
   - A. 继续放量到 50%，收集更多数据
   - B. 保持 10% 不变，等原因查清楚
   - C. 先回退让服务恢复，再去查原因
   - D. 马上写一个修复，直接发到全量

5. 一次发布里有新功能，还顺带删除旧表里的一批数据。工程师说：“有问题回退就行。”这个说法漏了什么？
   - A. 回退需要放行人再签一次字
   - B. 删数据退不回去，要单独发布
   - C. 新功能应该先放量到 1% 再说
   - D. 删数据之前要先通过持续集成

6. 一个功能完全按规格做完，评审和持续集成都通过，上线也很平稳。两周后发现几乎没人用。该回头查哪个关口？
   - A. 评审，代码负责人没有看出问题
   - B. 发布，放量计划做得不够细
   - C. 意图，这个问题值不值得解决
   - D. 分诊，监控没有及时发出告警

<details>
<summary>展开自测答案与解释</summary>

1. **D**。 自检不算关口。评审要由另一方来做：评审 agent 找缺陷，人看意图和风险，代码负责人批准。
2. **B**。 修改越大，评审这一关越容易失效。解法是把修改拆小，规定评审时长解决不了读不完的问题。
3. **A**。 并入主干不等于用户用上了。后面还有发布这个关口，放行之后还要分批放量。
4. **C**。 处理的原则是先恢复，再查因。停在 10% 查原因，这部分用户会一直受影响。
5. **B**。 回退只能换回旧版本的代码，删掉的数据回不来。这类修改叫单向门，要和别的修改分开，单独发布。
6. **C**。 意图和规格检验的是做的是不是该做的事。这里错了，后面每一关都只会认真检查一件错的事。

</details>

## 案例练习

### 这次发布签不签

你是放行人。一次修改已并入主干，工程师申请发布，单子上写着：“风险等级：低。放量计划：客户催得急，直接全量。回退方案：有问题就退回上一版。”你翻了合并请求：改动 2300 行，评审 12 分钟就批准了；其中一步会删掉订单表里一个“已废弃”的列；持续集成是绿的。

**请写出你的判断**

这次发布你签不签字？写出你的判断和理由，并把问题按严重程度排序。

<details>
<summary>展开案例参考分析</summary>

不签。至少有四个问题，其中第一个靠回退也救不了：

- **里面有一扇单向门。** 删掉的列回退也回不来，单子上的回退方案对它无效。这一步要拆出来，单独发布。
- **直接全量，没有分批放量。** 只在真实流量下才出现的问题，会一次落到所有用户身上。客户催得急也应该先放百分之一，看过指标再往上加。
- **风险等级填的是“低”。** 一次带删数据、改了 2300 行的修改不该算低风险。等级填低了，放量和回退的安排都会跟着偏松。
- **评审这一关很可能没起作用。** 2300 行在 12 分钟里读不完，批准不代表有人看过。修改应该拆小了再评审。

持续集成是绿的这一条本身没有问题，但它盖不住上面四条。排序的依据是能不能挽回：退不回去的排最前，影响面最大的其次。

</details>

## 复习

先不看题，凭记忆写出六个关口的名称，以及每个关口由谁签字。

1. 下面哪一个不算六个关口之一？
   - A. 计划
   - B. 分诊
   - C. 构建与自检
   - D. 发布

2. 计划这个关口由谁批准，重点看什么？
   - A. 工程师，看影响半径
   - B. 产品负责人，看值不值得做
   - C. 放行人，看回退方案
   - D. 代码负责人，看代码缺陷

3. 一次修改要满足什么条件，才能并入主干？
   - A. 评审通过就可以
   - B. 持续集成通过就可以
   - C. agent 自检通过就可以
   - D. 评审和持续集成都通过

4. 分批放量主要拦的是哪一类问题？
   - A. 规格一开始就写错了的问题
   - B. 只在真实流量下才出现的问题
   - C. 评审时没有读出来的代码缺陷
   - D. 测试没有写断言造成的问题

5. 在这六个关口上，agent 和人怎么分工？
   - A. agent 起草和执行，人签字
   - B. agent 签字，人负责执行
   - C. 简单的关口交给 agent 签字
   - D. 人起草，agent 检查后签字

<details>
<summary>展开复习答案与解释</summary>

1. **C**。 六个关口是意图、规格、计划、评审、发布、分诊。自检是写的一方自己查，不算关口。
2. **A**。 计划要在动手之前说清打算改哪里。工程师批准它，看这次修改会波及多远。
3. **D**。 评审和持续集成同时进行，两边都通过才能合入。
4. **B**。 这类问题前面的关口都拦不住，所以要先放百分之一，每一级停下来看指标。
5. **A**。 每个关口上都写着一个人的名字。agent 可以起草规格、写代码、先做评审，但签字的是人。

</details>
