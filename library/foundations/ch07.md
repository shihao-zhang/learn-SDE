## 讲义

agent 说测试通过了，但那些测试也是它写的，所以这一周要把验证拿回自己手里。办法有四条：先看到测试失败，再看到它通过；审测试本身，看断言是否检查了结果、有没有测出错的情况、是不是在测假的东西；对着规格里的验收条件，列一张“没覆盖什么”的清单；把检查写成命令，让 agent 每次干完活自己跑并贴出输出。调试有固定的四步：稳定地重现，缩小范围，提出猜测并设计能推翻它的检查，找到原因后先写测试再修。

## 术语

- **先失败再通过**。 先亲眼看到一个测试失败，再看到它通过，以此确认它真的在检查东西。
- **重现缺陷的测试**。 修缺陷之前先写的测试，缺陷还在时它失败，修好后它通过。
- **假测试**。 看起来在检查、其实什么也没检查的测试，比如把被检查的部分整个换成假的。
- **“没覆盖什么”清单**。 把验收条件一条条对过去，列出哪些条件没有测试，并写明打算怎么处理。
- **证据**。 检查命令实际运行后的输出，区别于“我已经验证过了”这样一句话。
- **调试**。 程序表现不对时，一步步找出原因的过程。
- **重现**。 找到一组固定的做法，每次照做都能让问题出现。
- **缩小范围**。 查清问题是从哪一步之后开始的，每次把嫌疑范围砍掉一半。

## 自测

1. agent 修了一个缺陷，汇报：“已修复，并新加了一个测试，测试通过。”你没有见过这个测试失败的样子。你该怎么做？
   - A. 接受，新加了测试并且通过，已经足够了
   - B. 让它再多加几个类似的测试，然后再合入
   - C. 让它在修复前的代码上跑这个测试，确认会失败
   - D. 让它把全部测试重新跑三遍，看结果稳不稳

2. agent 写的一个测试是这样的：“传入三条记录调用汇总函数，断言函数没有抛出异常。”这个测试的问题在哪？
   - A. 三条记录太少，至少要准备一百条才行
   - B. 只检查了没有报错，没有检查算出的结果
   - C. 汇总函数太简单了，根本不值得去测试
   - D. 测试的描述太短，别人会看不懂它在测什么

3. 要检查的是“抓取指标”这个函数。agent 的测试把这个函数整个替换成一个固定返回 42 的假函数，然后断言结果等于 42。你怎么判断这个测试？
   - A. 合格，抓取依赖网络，替换掉才能测得稳定
   - B. 基本合格，只是还少一个网络断开的情况
   - C. 基本合格，把 42 换成更真实的数字就行
   - D. 不合格，被检查的部分没了，它只是在测假的

4. 修缺陷的过程中，agent 说：“那个重现缺陷的测试，期望值写得不对，我顺手改了一下，现在通过了。”你该怎么回应？
   - A. 不接受，修的过程中不许它改这个测试
   - B. 接受，只要它把修改的原因解释清楚就行
   - C. 接受，测试写错了本来也是很常见的事情
   - D. 不接受，要它把这个测试删掉后重新修一遍

5. 规格有六条验收条件。agent 写了二十个测试，覆盖率 92%。你逐条对照后发现，第 4 条和第 6 条没有对应的测试。接下来怎么办？
   - A. 覆盖率已经超过九成，这两条可以先放过去
   - B. 逐条决定：补测试、写明手动检查，或接受风险
   - C. 两条都必须补上测试，否则这次修改不能合入
   - D. 让 agent 把覆盖率提高到百分之百，再来对照

6. 日报的总数昨天还对，今天错了，中间有八次提交。你已经能稳定地重现问题。按调试的方法，下一步做什么？
   - A. 在中间那次提交上检查对不对，把范围砍掉一半
   - B. 把问题描述清楚交给 agent，让它直接修好
   - C. 从最新的一次提交开始，把改动逐行读一遍
   - D. 先猜一个最可能的原因，直接改代码试试看

<details>
<summary>展开自测答案与解释</summary>

1. **C**。 一个从来没失败过的测试，你不知道它是不是真的在检查东西。再加几个同样没红过的测试，或者重复跑几遍，都回答不了这个问题。
2. **B**。 函数算出一个错的总数，这个测试照样通过。断言要检查结果，比如总额等于三笔之和。
3. **D**。 真正的抓取函数一行都没有运行，测试永远通过。“依赖网络所以要替换”最有迷惑性：这里被换掉的是要检查的那个函数本身。
4. **A**。 这个测试是判断缺陷修没修好的那把尺子。让修的一方改尺子，变绿就不再说明任何事。
5. **B**。 没有测试的条件有三种处理，关键是每一条都要有明确的决定。覆盖率只说明代码被运行过，回答不了哪条需求没人检查。
6. **A**。 重现之后是缩小范围：是哪一步之后开始不对的，每次砍掉一半。八次提交最多查三次就能定位。直接猜着改，跳过了定位这一步。

</details>

## 案例练习

### 这份验证能信吗

agent 汇报：“导出功能已完成并验证，3 个测试全部通过，覆盖率 95%，可以合入。”没有附命令输出。三个测试和功能代码同一次提交。  
测试一：传入三条记录调用导出，断言没有报错。  
测试二：把导出函数换成返回固定内容的假函数，断言返回值等于这段固定内容。  
测试三：传入三条记录，断言导出的文件有三行，金额合计为 600。  
规格有五条验收条件，其中两条是：记录为空时导出只含表头的文件；写入失败时给出提示。

**请写出你的判断**

这份“已完成并验证”能不能信？写出你的判断和每一条理由，并按严重程度从高到低排序。

<details>
<summary>展开案例参考分析</summary>

不能凭这份汇报合入。三个测试里只有测试三在检查真实的结果，而且它只覆盖了正常输入。按严重程度排：

- **两条验收条件没有任何测试。** 记录为空和写入失败都没有测。出错的情况最容易藏缺陷，这里一个也没检查。
- **测试二在测假的东西。** 导出函数被整个换掉了，真正的代码没有运行。它永远通过，什么也证明不了。
- **测试一只检查了没有报错。** 导出的内容全错，它也照样通过。断言要落在结果上。
- **没有一个测试见过失败。** 测试和功能一起提交，你没看到它们红过，也就无法确认它们真的在检查东西。
- **只有一句话，没有输出。** “已验证”和“覆盖率 95%”都算不上证据。覆盖率只说明代码运行过，要让它贴出检查命令的实际输出。

排序看的是哪个缺口最可能放过真实的缺陷：完全没检查的需求排最前，其次是看似检查了其实没有的测试，最后是证据的形式。回复时可以直接照这个顺序提要求。

</details>

## 复习

先不看题，凭记忆写出把验证拿回自己手里的四条做法，以及调试的四步。

1. agent 说“我已经验证过了”。这时你应该向它要什么？
   - A. 一份更详细的文字说明
   - B. 检查命令运行后的实际输出
   - C. 一句更加肯定的保证
   - D. 它写这段代码花的时间

2. 下面哪一项不在审测试本身要看的三样里？
   - A. 断言是在检查结果，还是只检查没有报错
   - B. 有没有测输入为空、网络断开这类出错的情况
   - C. 是不是把被检查的部分换成了假的再去测
   - D. 测试一共有多少个，全部跑完要花多少秒

3. “没覆盖什么”的清单，是对着什么列出来的？
   - A. 规格里的验收条件
   - B. 代码的全部行数
   - C. agent 的工作汇报
   - D. 上一次的提交说明

4. 调试的第一步是什么？
   - A. 直接读代码找可疑的地方
   - B. 猜一个原因然后动手改
   - C. 稳定地重现问题
   - D. 让 agent 把它修好

5. 调试时找到了原因。按方法，接下来先做什么？
   - A. 立刻动手修改，越快越好
   - B. 先写一个能重现它的测试，再修
   - C. 先把这次的原因写进约定文件
   - D. 先重新做一次缩小范围来确认

<details>
<summary>展开复习答案与解释</summary>

1. **B**。 你要的是证据。把检查写成一条命令，让它每次干完活自己跑，把输出贴出来。
2. **D**。 三样是：检查结果了吗，测了出错的情况吗，是不是在测假的东西。测试的数量和快慢说明不了它们有没有在检查。
3. **A**。 它对着需求列，所以比覆盖率数字有用。清单上的每一条都要写明：补测试、手动检查，还是接受风险。
4. **C**。 不能稳定重现，后面每一步检查的结果都不可信，修完也没法确认修好了。
5. **B**。 先写测试，看到它失败，再修，看它通过。这个测试之后会留在测试集里，防止同样的缺陷再出现。

</details>
