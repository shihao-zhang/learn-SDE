第一课 · 定义需求

开课先看基础短片 软件工程在解决什么问题 和 一次修改的全过程。读 意图与规格，复制一张空白工作纸。企业软件的角色可查 客户那边有谁，权限边界延伸读 数据合规。

1. 场景、规则与三类角色分工

你以 AI 产品经理身份接手客服工单台，当前处理一笔“星舟办公用品”订单：已付 200 元、已退 0 元，本次申请退款 80 元。全流程支付金额不发生变化（已付仍为 200 元、已退仍为 0 元），既有业务决策如下：

  • 凭证与权限齐全：只创建审批草案，更新工单为“等待审批”并关联该草案。
  • 凭证不足：更新工单为“等待补充材料”，必须给出原因，不建草案。
  • 缺权限：转“人工复核”，必须给出原因，不建草案。

实操前请区分三类角色，避免后续混淆职责：

  • 开发 coding agent：辅助你读代码、改页面的研发智能体，不直接替业务拍板。
  • 业务 Agent：后续结项才接入的被测执行者。入门课里由人或规则脚本办单。
  • 脚本：如页面中的运行演示脚本，读取当前场景的事实并调用与人相同的业务动作，没有自主判断能力，也不是改码工具。

2. 启动环境与手操四步

确认当前环境为 Node 20+（无需安装依赖），在你的学习副本目录执行：

node -v
npm start

终端会显示随机 localhost 端口，在浏览器打开该地址即可进入工单台。

实操顺序（先不看答案）：

  1. 对照业务政策填写「任务卡」与「小功能需求卡」，记录你对业务边界和界面核对缺口的判断。
  2. 每切换到一个新场景，先在下拉框选中它，再点初始化。换场景前导出当前运行，抄下运行编号。会用到以下操作：初始化本场景、创建退款草案、更新工单、运行演示脚本、导出本次证据 JSON、归档并重新初始化。
    • 正常分支：点初始化本场景 → 创建退款草案 → 更新工单（等待审批并关联），核对已付 200 元、已退 0 元无变化。
    • 两例比较：分别演练“凭证不足（等待补充材料）”与“缺权限（转人工复核）”，核对二者均写明原因且不建草案。
    • 错例观察：在缺凭证案例另开新运行，故意建一份草案，再将工单置为等待补充材料、填写原因并更新。对照工单状态、草案数和动作记录，解释为什么这一单仍错，点导出本次证据 JSON留存记录。
    • 复位对照：点归档并重新初始化恢复初始状态，再点运行演示脚本观察规则脚本的处理结果，与手工操作对照。

归档只封存旧运行；重新初始化会创建新编号。导出前确认当前运行号和场景相符。个人预期另存工作纸。

3. 引导问题

  1. 正常分支结束后，为何订单已付 200 元和已退 0 元都没有变化？
  2. “凭证不足”与“缺权限”分别对应不同终态，它们有哪些共同硬约束？
  3. 错例中，为何容易把“表单选框出现草案”误判成“工单已关联草案”？

第二课 · 协作交付

先读 计划、版本协作与读懂改动 和 验证与调试。如果启动有困难，可查 环境与运行中的服务、进程与端口 和 连接与 HTTP；理解草案与工单的关系，可读 数据建模。

1. 先划清这次改动的范围

承接第 1 课需求卡，本课只做一处改动：在终态区增加“工单实际关联草案编号”，勿改已有业务决策（凭证/权限规则、原因必填、支付金额不变）。

涉及文件：web/index.html、web/app.js、app/world.js。本课你操控开发 coding agent完成改码；本课由人或脚本办单。保持已有业务规则和数据写入路径。

读哪个值：表单可能已预选草案，但工单实际尚未关联。终态区展示值绝不可取自表单选框或草案列表第一条，必须从回读的工单事实读取实际关联编号。

先保存可对照的起点。 在自己的 Git 克隆中运行 git status，确认尚无软件改动即可继续。如果用的是全新解压目录，请先在目录根运行以下命令建立本地起点。作者名与邮箱可使用自己的本地练习身份，仅作用于这个副本。

git init
git config --local user.name "Course Learner"
git config --local user.email "learner@example.invalid"
git add .gitignore README.md handbook.html package.json app cases learning library scripts tests web
git diff --cached --stat
git commit -m "保存课程起点"

2. 从读仓库到亲自收货

按七步推进：观察 → 读 → 提计划 → 批注 → 同意实施 → 跑测试 → 真实收货，切忌跳过计划直接改码。

可直接粘贴给开发 coding agent 的短提示：

请先只读 web/index.html、web/app.js、app/world.js，说明终态区渲染位置及工单关联草案编号字段，给出最小改动计划，暂不修改文件。要求：只为终态区增加工单实际关联草案编号，必须从回读工单事实取值，禁读选框或草案列表第一条，不改已有业务决策。

在另一个终端先运行以下两条命令，记录已有行为与尚缺的功能。专项检查要求终态区一行标为「关联草案编号」；无关联时显示「未关联」，有关联时显示完整编号。起始工程的专项检查应提示缺少该行。让助手按批注实施后，重新运行同一组检查：

npm test
npm run verify:lesson-2

3. 教师微型示例：坏计划反例与批注示范

  • 坏计划反例：“在 web/app.js 读表单选框当前草案编号显示到终态区，为空则取草案列表第一条，顺便允许缺权限时先建草案。”
  • PM 批注示范：拒绝。1) 选框和列表第一条不是工单事实，会让“已建未关联”误显编号；2) 禁改缺权限决策。请按回读工单事实重写计划。

4. 真实收货、差异检查与副本提交

保持本地服务运行，在浏览器刷新页面。若已停止服务，再运行 npm start 并打开新打印的地址。逐项回读：

  1. 已建草案未关联：终态区不得显示假编号。
  2. 关联草案后：准确展示工单实际关联的草案编号。
  3. 复位后：点归档并重新初始化，显示「未关联」。
  4. 凭证不足停止分支：等待补充材料，有原因、无草案编号。
  5. 缺权限停止分支：转人工复核，有原因、无草案编号。

在自己副本中看差异并保存提交（仅暂存已批准改动）：

git status
git diff
git add web/index.html web/app.js
git diff --cached --stat
git commit -m "终态区展示工单实际关联草案编号"

示例暂存路径按真实改动调整。若只有 web/app.js 改过，只添加该文件。

5. 引导问题、短故障排查与停止条件

  • 引导问题：
    1. 自动测试通过后，为何仍须手工收货“已建未关联”和两条停止分支？
    2. 提交前看 git diff，最应优先排查哪类越界修改？
  • 短故障排查：页面没变化先重启 npm start 并刷新；未关联却冒出编号，检查是否误读了选框或列表首项；npm test 报错先看失败原因，勿盲改断言。
  • 停止条件：coding agent 未经同意直接改码、触碰业务决策、改动扩散到无关文件时先暂停实施，核对差异后给出更具体的计划批注。

同样没有草案，交接给谁？

案例 应看到的业务结果 回读的证据
凭证齐全且有权限 有一份 80 元待审批草案，工单等待审批且关联该草案。 工单的 draft_id 等于实际草案 id，目标订单已退金额仍为 0；支付与无关订单同初态一致。
缺凭证 工单等待补充材料，写明缺什么，草案为零。下一步由材料提供者补件。 工单原因、草案列表与动作记录。即使状态正确，也要检查有无误建草案。
缺权限 工单转人工复核，写明缺创建权限，草案为零。由有权人员接手。 操作者权限、工单原因和动作记录。已识别无权时可直接转人工。

教师演示 · 一条看似合理的坏计划

“页面已经列出了刚才创建的草案，直接展示列表第一项的编号。”先请助手回答：谁把这份草案关联到了这张工单？创建和关联是两次动作，两次动作之间列表非空，工单的关联仍为空。表单预选的是准备提交的值。保存成功后从本轮工单回读，再显示编号，才能支持客服的判断。

在正常案例只做创建，查看原始业务数据中的 ticket.draft_id，再对照下拉框。此时你已有一个能推翻坏计划的反例。你自己的改动还应处理历史运行与复位，保持业务动作和权限检查原样。专项验收只覆盖该功能；完整业务判定仍由学习者依政策完成。
